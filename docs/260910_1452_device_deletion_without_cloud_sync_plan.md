## 1. 按用户意见调整目标

用户否定“异常非空 Space 直接删除记录”的方向。本次应修复共享设备删除流程：Space 同步失败时，仍可普通删除设备；不能安全发送 Reset 时，允许用户明确选择强制删除设备记录，实体设备自行复位。Space 删除继续要求设备已经清空。

区分三个独立结果：设备是否真正 Reset、本地设备及引用是否已清理、云端是否已经同步。云端失败不能阻止前两者；本地记录移除不能冒充设备已经复位，也不能冒充云端同步成功。

## 2. 当前卡点与证据

- `DevicePermanentDeletionContext.prepare()` 同时要求本地删除的身份/持久化条件与活动 Mesh 网络对象、当前 Network ID 匹配。缺少目标密钥或活动网络不匹配，会在尝试 Reset 之前失败；本身没有检查 HTTP 同步是否成功，问题是共享了不该共享的准备条件。
- Lights 批量删除先要求所有 context 的 `isPrepared` 为真，失败就显示 `configuration_deletion_cleanup_pending` 并退出，用户无法到达后续 Force Delete。
- `prepareForForceRemoval()` 仍调用同一个 `prepare()`，没有独立的本地删除资格，因此也被当前密钥/网络状态卡住。
- `complete()` 和生命周期协调器要求归一化后的完整拓扑有效、无额外 repairs。与本次选中设备无关的旧悬空引用也能阻止清理完成；不能简单删掉所有校验，否则会顺便修改其他设备。
- 批量强制删除调用 `forceRemove()` 后不区分返回 nil 的原因，随后按全部失败地址从 UI 移除设备。nil 既可能代表清理失败，也可能代表没有返回同步任务，结果表达不足。
- 当前 journal 的 cleaned 与云端确认已经部分解耦：cleaned 后仍保留条目，直到对应提交回读确认。这一机制可保留并完善，不需要把设备删除强绑到上传成功。

## 4. 设备删除的共享流程

### 4.1 分开本地准备与 Reset 条件

本地准备只要求：当前账号/区域、Site/Space、设备实例身份能够确认；有删除权限；能读取目标持久化数据并写入检查点和删除意图。云端同步失败、缺 NetKey/AppKey、密钥冲突、活动代理不在本 Space，都不是本地强制删除的否决条件。

Reset 另行检查可用且正确的 Mesh 密钥和当前网络/代理上下文。网络条件满足时保持原普通删除：成功后清理本地；失败的设备可选择重试或 Force Delete。条件不满足时，直接提供对选中设备的 Force Delete 确认，不先发送注定无效的 Reset，不借用另一 Space 的 Key。

写库失败、身份无法确认、账号/权限变化仍需停止并显示真实原因。用户授权跳过的是设备通信/云端同步，不是跳过持久化或删除权限。

### 4.2 强制删除按设备实例持久化

从数据库加载明确属于目标 Site + Space Network ID 的对象，按设备 UUID、地址及实例信息校验，使用该作用域删除；不依赖当前活动 `MeshNetwork`，不按共享 Key Index 定位，不仅按地址删除。

当前 SDK 的部分节点删除接口按 Site + 地址操作。实施时先核对其边界：必须在受控操作内验证当前持久化实例，防止旧任务删除同地址新设备；必要时在现有 SDK 工作区增加最小的实例/子网限定接口，不自行拼接修改不明数据库结构。

删除日志区分“Reset 准备”和“用户已确认强制删除”。后者落盘后，即使进程中断且节点仍存在，也必须能够重放，不能像当前普通 prepared 条目一样被 resume/deinit 当作取消直接抹掉。

### 4.3 只清理所选设备的引用

清理目标设备所有元素地址的 Group Path/Zone、Space Trigger Zone、Scene、Schedule、代理绑定、传感器和分发等已有扩展引用。保留未选中设备、Group/Scene 定义和其他 Space 数据。

为确认删除引入专用的局部清理校验：比较删除前后，只允许目标设备及其引用消失；证明目标在数据库中已不存在、其引用已清除，并且没有引入新错误。与所选设备无关的既有悬空引用保持原样，继续记录为独立拓扑问题，不能阻止本次设备删除完成，也不能顺手被全局 normalize 修复。

不整体放宽普通编辑/导入的拓扑检查。无法解码或无法证明引用清理完成时，记录“设备已移除、清理待重试”，保留日志并禁止误报全部完成；不要求先修复云端同步才可重试本地清理。

### 4.4 删除结果与 UI 一致

删除操作返回明确的逐设备结果：已重置并清理、已强制移除并清理、已移除但本地清理待重试、未删除。拓扑同步任务为附属结果，不能再用 nil 判定整个删除是否成功。

只把持久化确认已移除的设备从列表删除；未删除项继续保留并选中以便重试。没有剩余设备或没有邻居同步任务，也应能正常完成。剩余设备配置的后续同步不作为已经完成的设备删除的前置条件。

共用入口覆盖 Lights 全选/部分选、单灯详情、通用 DeviceProtocol 与 Dongle 删除。现有 Force Delete 确认与手动复位文案优先复用；新增结果/错误文案同时提供英文和简体中文。

## 5. 云端、重新进入与空 Space 删除

本地删除完成后，只推进本地变更版本，保留设备删除凭据与待上传状态；不能更新上传成功时间或因为密钥缺失伪造完整配置。

重新进入 Space 时，先重放本地已确认的删除，再处理远端数据。旧远端快照和 pending-import、旧上传回读不能复活已删除设备或清掉更新的删除记录；当前被 hasPendingImport 一概挡住的情况，要先暂停旧导入、使其异步上下文失效，并明确处理已落盘的中间状态，再执行删除，不直接移除 guard。

本地已确认空且设备引用清理完成后，可以执行普通 Delete Space，不能再要求完整 Space 配置先上传成功。仍然走现有独立空间删除接口与 owner 权限，保留服务端成功之后清理本地的顺序。

**接口验证是这条链路的关键验收项：**本地设备已强制删除，但云端可能仍保存旧设备。如果 `/sitespace/spaces/delete` 因远端非空拒绝，客户端修复不能宣称全流程闭环。此时需核实已有设备记录删除 API，或由服务端提供按已选设备身份删除的能力：先删除云端对应设备记录，再普通删除空 Space。不得恢复“非空 Space 强制删除”、新增未经证实的 force 参数、伪造密钥或把本地计数零当作云端已空的证据。

当前没有后端设备删除接口契约，不能编造接口路径。本轮规划不调用生产删除接口。
