# Proximity 兼容修复方案：仅修改 App，建议全部编辑端同步升级

日期：2026-09-07。基线：`fd520c9`。本方案依据用户最新约束，取代原报告中的服务端改造建议。用户已授权实施；实现与验证状态见 [实施记录](260907_1400_app_only_proximity_compatibility_implementation.md)。

## 1. 已确定的范围

- 服务端无法改造，沿用现有 GET、Space 全量上传和 Site 嵌套 Space 上传接口。
- 建议 A、B 及其他有编辑权限的手机覆盖安装本次修复后的新版；仅升级至存在本轮缺陷的 fd520c9 不能视为修复完成。
- 目标为新版正常展示 Profile、Group Path、Group Trigger Zone、Space Trigger Zone，正常编辑、保存、导入和升级不会制造默认 Profile 或删除不确定的配置。
- 对未升级旧版提供尽力保护，不承诺旧版任意编辑/设备同步都安全。不新增强制升级的服务端门禁或权限系统。
- 保留历史旧格式读取能力；不为了让 1.2.0 继续编辑而合成 Group Zone、改动真实 Profile 类型或增加两个独立可写的 Zone 副本。
- 不依赖服务器保留新增的 revision、writer capability、删除操作标记或其他未知字段。

## 2. 兼容边界

同步升级可以减少旧算法继续覆盖数据，但不会自动找回已删除的数据，也不会自动修复现存的 Profile 持久化缺陷，因此仍需以下 App 修改。

仅 App 修改无法实现服务器原子的冲突检测。上传前 GET、上传后回读和客户端串行操作可以缩小覆盖窗口、发现异常，不能保证另一台手机不会在验证后再次上传。正常多人编辑继续依赖当前的 Editor 使用流程与及时同步；混用旧版期间不承诺无损并发。

恢复需要至少一份确实完整且适用于当前 Space 的逻辑配置：A/B 本地、先前保存的备份或服务器当前完整数据。所有副本都已损坏时，不能仅根据设备邻居表无损重建原 Profile 参数、Path 顺序及 Zone 分组。

## 3. 第一阶段：修复已确认的 App 数据安全缺口

### 3.1 Profile 不再静默退化并上传

涉及 `Database.swift`、`MeshNetwork+SunSmart.swift`、`ImportData.swift`、`ExportData.swift`，以及保存 Group/Profile 的直接调用方。

1. 为“加载已有 Group 的 Profile”提供明确结果：完整、缺失、损坏；默认 Profile 只用于明确的新建流程，不用于伪装已存在 Group 的加载成功。
2. GroupInfo.profileId 与 Profile 在同一个 App 数据库事务内保存，错误逐层返回；数据库连接不存在也必须失败，不能因可选调用未执行而返回成功。
3. 导入不能因 profile/type/id 缺失就把已有 Proximity Group 当默认 type 1 正常保存；无法确定的类型进入待核对状态。
4. 已有 Profile 加载失败、引用不匹配或保存失败时，阻止该 Space 的云端导出与相关设备配置，保留可用快照和待同步状态。
5. 添加故障诊断：Group 身份、预期 Profile id、解析/加载/保存失败类别。若确认设备数据库含历史 regulatorAccuracy 非空列，再按实际列结构迁移；不把未证实的历史问题当成本次唯一原因。

### 3.2 导入与显式用户编辑使用不同清理规则

涉及 `ImportData.swift`、`ProximityLightingTopologyReconciler.swift`、`ProximityLightingLifecycleCoordinator.swift`、`Node+SyncData.swift`。

1. 将明确的本地操作（Profile 降级、删除 Group/Node、移除成员、清空 Zone）与外部快照导入/加载/升级区分，前者继续按完整生命周期清理关联数据。
2. 按用户补充要求，以数据完整、字段合法及引用一致作为判断条件。不能仅因 type 7/8 变成 1、Profile id 改变或拓扑被明确清空而拒绝导入。完整的本地及远端 Profile 切换均继续同步。
3. 缺失/非法 Profile、非 Proximity 类型仍携带 Group Path、损坏的拓扑/引用、持久化失败需要保护。服务端没有可信操作来源时，无法区分“已经完整写成 type 1 的旧版错误”与合法切换；不根据类型猜测意图，也不自动复活合法删除。保存原始副本用于恢复依据。
4. 有本地完整副本时，疑似退化导入保持可进入查看，先保留完整配置，不执行拓扑清理、不生成 Disable/缩减邻居任务、不自动把混合数据全量上传。
5. 没有完整副本时，将未知拓扑与明确空配置区分。允许展示可解码数据及异常状态，但不得把未知配置当成需要禁用设备的目标。
6. 保护状态须持久化，并由共享导入、生命周期、导出、同步任务入口执行；覆盖 More SAVE、Group/Profile 编辑、Device Restore、成员变更、延期同步和导入后的修复同步页。

产品上只有异常冲突需要提示；正常改名、正常保存和明确的本地删除保持现有流程。只靠检测 type 1 并一律拒绝，不是可接受方案。

### 3.3 导出不再修改业务配置

当前 `SpaceData.export()` 会调用生命周期 commit，可能在序列化期间清除不合格 Group 的拓扑、写数据库并标记 dirty。改名触发导出因此可能带来额外删除。

规划调整为：导出读取一份一致的快照并验证，再序列化；不借导出执行业务清理。需要的拓扑变更在对应明确操作中先完成。发现需要破坏性修复或缺失 Profile 时，导出返回失败并保留原数据，不能静默规范化后上传。

沿用当前 `spaceData` 的已知云端结构，并保留旧顶层格式导入支持。nested/root 同时存在且冲突时，不能拼接成一份看似完整的数据；应按明确来源规则处理并记录异常。暂不增加面向旧 1.2.0 编辑能力的双写。

### 3.4 上传只确认实际提交的数据版本

涉及 `CloudSynchronizationManager.swift` 和统一导出入口。

1. 每次提交保存实际导出时的客户端代次/时间戳与 Proximity 内容摘要；HTTP 成功后只能确认那次提交，不能用回调时对象最新的 lastUpdate 清除后续修改。
2. 使用现有 GET 对关键 Profile/三类拓扑做必要回读核对。比较规范化内容，忽略服务端派生字段，保留 Path 的顺序语义。
3. 回读不一致或超时要区分“请求已被服务器接受”与“内容尚未确认”，保留可恢复快照和待核对状态；不自动无限重试旧整份快照，避免反复覆盖其他端。
4. 保护覆盖普通 Space 上传、Site 嵌套上传、重试和退出时加速发送。嵌套请求包含未校验 Space 时，不能绕过保护发送；合法的其他 Space 操作按现有接口能力保留。
5. 如果现有服务器不能完整返回四类配置，回读必须暴露该事实；仅 App 修改不能承诺全新客户端获得服务器已经丢失的字段。

## 4. 第二阶段：覆盖安装、导入失败与恢复

### 4.1 保存可恢复副本，避免升级先上传坏数据

在首次执行受影响 Space 的导入、上传或设备配置前，建立校验与迁移状态。先保存当前原始配置，再决定它是否可以作为“最后完整副本”；不可把升级时已经损坏的数据仅因成功序列化就认证为完整。

CloudSynchronizationManager 的 handles 是内存数组；源码还会根据持久化 needUploadCloud 等状态重新生成任务。因此升级保护不仅检查现有内存 handle，也要覆盖从 dirty 状态重新入队、进入/退出 Space 和嵌套 Site 提交。

待上传修改应被隔离保存，不清空全部 dirty。关键配置和成员归属与云端一致时，保留本地名称等修改并允许上传；不一致时阻止升级后的旧 dirty 直接全量上传，留存原始快照。没有修改前基线，无法确认旧 dirty 是否只有名称修改，因此不自动把其名称覆盖到不同的远端基线。

### 4.2 导入失败保护要覆盖两个数据库与内存

当前业务表在 `sunsmart.sqlite3`，SDK Mesh 数据在 `mesh.sqlite3`，由不同连接管理。不能宣称一个 App 数据库事务即可让整个 Space 导入原子化。

实施时分两层处理：

- GroupInfo/Profile 等业务表在同一连接事务内保存并校验。
- 全量导入在应用前完成解析与可用性验证，按 Space 串行应用，保留两个存储与内存状态的一致恢复点；记录应用阶段，失败/崩溃后从恢复点恢复或继续完成，禁止未完成状态被导出或用于 Mesh 配置。

不直接复制可能仍在写入的裸 SQLite 主文件充当完整备份；实现须使用一致的数据库备份/快照方式并验证回读。优先使用 App 与现有 SDK 能力；若需要修改 SDK，另行确认范围，不在本方案中默认展开。

### 4.3 A/B 升级与恢复顺序

1. 保留现有安装和本地数据，在能够保留备份的前提下覆盖安装修复版。
2. 建议所有编辑端同步升级；在恢复前不继续用旧版执行 Group/Space Zone SAVE 或设备同步。
3. 检查 A、B、服务器可用副本，选定完整且经确认的配置，不仅比较时间戳。
4. 先在一个编辑端恢复并上传，再读回核对 Profile、Path、Group Zone、Space Zone。
5. 其他端接受已确认数据并处理待上传修改，最后读取/同步真实设备状态。
6. 若无完整副本，明确哪些数据仍在、哪些需要重新配置，不自动创造一个 type 7 Profile 假装已经恢复。

## 5. 本轮不再实施的原建议

服务端 canonical 新存储、revision/CAS、旧客户端字段白名单、服务端 PATCH 接口、旧 GET 投影和服务端强制升级均移出范围。原始分析报告中这些内容仅用于解释能力边界。

App 内部可保留本地基线与摘要，但它们不是服务器 revision。若写入格式以后新增任何操作来源字段，必须先验证现有服务器确实往返保留，不能作为本轮保护成立的前提。

## 6. 验证与完成标准

优先覆盖有实际行为的测试：

1. 旧格式完整 Group/Path/Zone 导入，新增 Space Zone 后存储与重载完整。
2. 重现无 schema、根 triggerZones 为空、Profile 缺失/默认回退，确保不清理原完整数据或生成破坏性设备任务。
3. Profile 保存失败、孤立引用、非法 type、数据库连接不可用，不产生成功上传或默认业务 Profile。
4. 明确用户降级/清空仍成功；来自其他手机的合法删除可接受，不能被永久保留策略阻断。
5. 导出前后逻辑对象、数据库与 dirty 状态不因归一化发生变化。
6. 上传期间再改名/改配置，旧回调不清除新 dirty；回读不一致不进入无限覆盖重试。
7. 带旧 dirty 状态升级、无网络、应用中断、重启和 Site 嵌套上传不能绕过校验。
8. 两存储应用阶段故障后可恢复一致状态，不把部分导入结果用于设备或云端。

随后使用隔离测试 Space 验证现有服务端四类配置的真实往返与双修复版 A/B 的交替编辑；混用旧版只做降损验收，不作为无损并发承诺。真实设备核对 Enabled、Relay、Neighbors 与页面显示。

共享代码检查五品牌影响；按 AGENTS.md 直接运行 generic iPhoneOS xcodebuild。新增用户可见异常/恢复提示复用国际化 key，缺失时同步 English 与简体中文；实际设备验证完整交互和布局。
