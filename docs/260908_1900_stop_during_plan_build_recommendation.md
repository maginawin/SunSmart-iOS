# 后台任务构建期间 STOP 竞态修复建议

## 结论

推荐修复，维持 P2，建议在本次同步重构合入前处理。触发依赖后台构建与用户 STOP 的先后顺序，但后果是明确停止后自动恢复配置发送，破坏用户停止语义。

## 当前源码证据

- `SyncDevicesViewController.viewDidLoad` 将当前同步状态传给后台构建器。
- `SyncExecutionSession.stop()` 通过 `markStopped()` 将当前状态改为 `.syncFailure`。
- `installTaskPlan` 仅检查是否离开页面，然后无条件用构建结果的 `initialState` 覆盖当前状态；当结果为 `.inSync` 时自动启动同步。
- 构建器也可能因构建失败返回 `.syncFailure`，修复必须保留该失败语义。
- 现有 `SyncRunLifecycleTests` 覆盖离页后交付、正常安装和等待手动重试，未覆盖构建期间 STOP 后交付。

既有审查文档 `260908_1810_review_e40ab02.md` 记录 InstallationHarness 复现结果为 `starts=1, state=inSync`。本次核对源码与现有测试，未重新执行复现脚本、构建或真机验证。

## 建议的最小范围

1. 在结果安装入口尊重当前停止/取消状态，禁止迟到结果恢复自动同步，同时保留构建失败状态和离页拦截。
2. 处理新安装任务的停止展示与手动重试资格：STOP 发生时任务可能尚未安装，仅保留会话状态可能遗漏这些任务的状态处理。
3. 补充“开始构建 → STOP → 交付结果”确定性回归，断言不自动启动、保持停止状态，并验证用户主动重试仍可工作；保留正常安装、构建失败和离页路径的覆盖。

本次仅提供修复建议，未修改生产代码或测试。
