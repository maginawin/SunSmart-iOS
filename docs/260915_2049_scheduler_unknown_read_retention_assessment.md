# Scheduler unknown 补读逻辑保留评估

## 结论

**保留逐 Model 的 unknown 语义、补读能力及操作前读取保护；优化 Timed 页面自动补读的范围和调度。替代机制完成前，不建议直接删除页面入口。**

本次仅做代码评估，没有实施修改或运行设备验证。

## 为什么仍然需要

1. 节点级 `schedulerActions` 不包含每个 Scheduler Model 的完整状态，无法证明日程写在正确的 Model 上，也无法证明其他 Model 没有同 index 残留。不能用旧记录直接把 unknown 变为已同步或已知空。
2. 当前 [ImportData.swift](../SunSmart/Common/Data/ImportData.swift) 的日程导入段（第 2236、2772 行附近）恢复的是节点级记录；[ExportData.swift](../SunSmart/Common/Data/ExportData.swift) 第 665、1106 行附近同样导出节点级记录。因此，缺少本地逐 Model 缓存的导入仍可能产生 unknown，不能将补读视为只服务于 7 月旧版本的一次性迁移。
3. [ScheduleServer.swift](../SunSmart/Main/Timed/Model/ScheduleServer.swift) 在删除日程前读取未知状态；编辑日程、退组、删组也有对应读取入口。读取失败时停止后续相关修改，可避免未知状态被当作“没有需要清理的设备日程”。
4. 本地 SDK 已支持逐 Model 持久化、已知空缓存，以及全新配网后的已知空初始化。正常读取并保存后无需反复补读；缓存持续丢失时应追查恢复、导入覆盖、Model 解析或读取失败原因。

## 当前页面自动补读的不足

依据 [TimedViewController.swift](../SunSmart/Main/Timed/Controller/TimedViewController.swift) 第 232～305 行：

- 每次页面出现都会重新检查；筛选范围是全空间真实节点，排除 Dongle，但没有按当前日程关联、历史残留或待清理任务缩小范围，也没有无日程时的提前返回。
- 全局 Mesh 命令忙时每 0.5 秒等待重试；已有页面实例并发保护，但没有跨页面的失败冷却或统一去重机制。
- 任一 Model unknown 就对该节点执行完整读取。根据本地 SDK `MeshScheduleServer.getSchedule`，读取包括节点全部 Scheduler Model 的 Register，以及 Register 中有效 index 的 Action。
- 失败节点保持 unknown，下次进入可再次读取；已提交的读取在离开页面时没有由这个控制器取消。
- 完成后调用 `updateUI()`，会重新触发日程卡片同步状态计算。

这些会增加蓝牙通信和重复刷新成本。不能把整段蓝牙等待时间等同于主线程阻塞，也不能仅凭此静态分析认定它是此前十秒卡顿的主要原因；已有 trace 分析将主要耗时定位在卡片同步判定中的成员扫描。

## 建议的保留方式

### 应保留

- unknown 与已知空、已确认差异的区别。
- 逐 Model 的同步与残留检查。
- 编辑移除旧目标、删除日程、退组、删组等相关操作前的读取保护。
- 读取成功后的缓存保存、失败后的未知状态与重试能力。

### 应优化

- 页面先展示已有数据；未知状态显示为待检查，避免直接表达为已确认同步失败。
- 自动补读优先覆盖当前日程目标、历史记录、待删除关联及残留检查所需节点。不能仅按当前目标筛选，否则会遗漏退出目标后的残留。
- 使用统一调度，对空间和节点去重，分批处理，限制失败重试频率；用户主动操作优先于页面预读。
- 页面离开或切换空间后停止追加不相关的预读任务；取消应使用命令队列支持的边界，不能直接破坏正在处理的全局 Mesh 回调。
- 成功后按状态变化刷新受影响项，减少全列表重复计算。

### 不建议直接删入口

当前列表的状态判断仍依赖逐 Model 缓存，部分 unknown 节点可能一直显示待同步；全空间残留检查也可能因 unknown 暂不产生清理差量。操作前读取入口并不自动证明已覆盖所有列表检查和历史孤立节点。

若要关闭页面预读，需要同步落实未知状态展示、按需读取及残留覆盖，否则只是推迟了问题。
