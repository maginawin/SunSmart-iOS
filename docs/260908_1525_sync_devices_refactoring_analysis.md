# SyncDevicesViewController 长度与重构方案分析

分析时间：2026-09-08。范围：`trigger-zone-sep` 当前工作区源码，包含分析开始时已有暂存的进度刷新修改。本次仅新增分析文档，不修改业务代码、SDK、工程配置或现有暂存内容。

## 结论

当前文件已经过长，建议安排分阶段的职责重构。判断依据是任务生成、执行调度、设备协议策略、结果回写和 UI 生命周期集中在同一个控制器，且通过同一组可变模型相互影响。

不建议一次性重写。推荐先抽离任务构建和专用策略，再抽离同步会话；现有页面入口、任务顺序、成功判断和回调约定保持兼容。单纯拆分 extension 可以改善定位，但不足以解决职责耦合。

本结论是静态维护性评估，不代表已经证实当前代码存在死锁、数据竞争或性能瓶颈。

## 2. 具体的耦合证据

### 2.1 数据源构建同时承担业务规划

`setupDataSource()` 不只是把数据展示到表格，还决定配置与删除的顺序、成员变更上下文、跨 Group 邻近照明补充任务、PIR 前后置保护、网关恢复和消防任务。电池开关配置分区还特意排在删除分区之前（约 685–690 行）。

`getSyncDeviceModel(...)` 已复用 `Node.getSyncData(...)`，随后将业务数据转换为操作、步骤和依赖。初始化、入组、退组有不同的先后约束，部分退组清理步骤明确不阻塞退组。重构应复用现有业务 planner，不在新 Builder 再计算一套同步需求。

Profile 依赖规则分别出现在独立 `.profile` 分支（约 225–287 行）和普通设备构建（约 1389 行起）：前者建立步骤依赖，后者建立任务依赖。二者有共同业务规则，但展示粒度不同，应先验证生成结果，再决定是否提取共同依赖描述。

### 2.2 UI 模型同时是执行队列

`getNextHandleModel()`（3448 行）遍历 `sections.allModels`，通过类型转换寻找设备和任务。`SyncDevicesSectionModel.allModels`（模型文件 1097 行）同时受 Proxy、Group 和 `prefersDevicesBeforeGroups` 排序影响。

因此，分组模型的排列会影响执行顺序。`rowModels` 则另外依据展开状态生成可见行，不能简单用它替换 `allModels`。

设备和步骤的 `state` 是子任务状态的聚合结果，模型里还保存选择、展开、父级引用、依赖引用、失败次数、跳过标记与动画。仅增加一个 ViewModel 并继续共享这些可变对象，无法形成清晰的执行边界。

### 2.3 执行循环负责过多专用行为

`startSync()` 内部同时包含：

- 配置可用性和蓝牙检查、网关离线处理。
- 普通 Mesh 操作、服务器授权任务及消防本地空消息任务。
- 初始化成功后追加消息、Scene 状态更新、功率校准错误处理。
- Lux 锁状态记录及 Daylight Recall 恢复。
- ACK 后更新 Node 数据和同步缓存，再判断业务操作是否成功。
- 消防删除清理自动重试、电池开关失败传播和等待时序。
- 展开当前设备、刷新进度、发送通知、成功回调及自动恢复重试。

例如普通操作通常要求“消息结果成功且业务操作状态成功”；网关恢复初始化、电池开关自身配置和消防删除清理存在专用判断（3159 行起）。不能在抽离 Executor 时统一简化为“ACK 成功”。

### 2.4 会话状态与线程归属分散

`viewDidLoad()` 在后台构建模型；`startSync()` 使用后台队列、信号量、Mesh 回调；服务器授权又桥接 Swift Task；UI 在主线程读取相同模型，STOP/重试入口也会修改状态。

当前已有 `syncRunIdentifier` 拦截旧轮次回调，这是必须保留的保护。但状态所有权没有形成独立边界：主线程事件、后台循环、延迟重试和结束阶段需要放在一起阅读才能判断生命周期。

这构成重构和回归验证的重点，不能仅凭静态阅读宣称已经发生竞争或死锁。第一轮职责抽离也不宜同时把所有 GCD、信号量和 Mesh 回调改写为 actor/async-await。

### 2.5 退出不是简单关闭页面

`backAction()`（2056 行）先使当前轮次失效、安排 PIR 恢复并解锁 Lux，然后汇总每个设备的成功与失败操作。有 `backActionCallback` 时把退出交给调用方；没有回调时才走 `closeAfterSync()`。

当前 `DeviceProtocol.syncPermanentDeletionPeers(...)` 已验证存在一次性 finish，并先 pop 同步页再执行调用方 completion。`SpaceViewController` 也有成功后自行 pop 的入口。不能在控制器中新增统一“成功即关闭”，否则会改变多处调用方约定。

### 2.6 共用功能的归属不合适

文件尾部定义了 `Node.sendHandleCompleteIdentify(...)`，但它也被 `ReadDevicesDataViewController` 和 `LightSensorCalibrationViewController` 调用。该能力适合放到共用 Node 扩展文件。

`SyncDeviceStepTaskModel.resyncRelevanceCheck()` 也位于控制器文件尾部，实际属于任务重试依赖规则。它可以随重试策略抽离，而不是继续让模型依赖控制器文件里的实现。

## 3. 可选方案

| 方案 | 做法 | 收益 | 成本与限制 | 建议 |
| --- | --- | --- | --- | --- |
| A：按主题拆文件 | 拆分 Table、TaskBuilding、Gateway、EmergencyFire 等 extension，迁出共享 Node 扩展 | 阅读定位更方便，行为改动较少 | 所有方法仍共享同一控制器状态；跨文件 extension 访问现有 private 成员需要处理访问边界，不能直接机械移动 | 可作为小范围整理，不作为最终方案 |
| B：按职责渐进抽离 | 任务构建器、专用策略、同步会话、UI 渲染分阶段迁出 | 实质减少耦合，可以单独验证任务顺序、重试和结果判断 | 需要建立行为基线，处理旧模型适配；每阶段都需回归 | **推荐** |
| C：独立同步领域模型与执行引擎 | 独立 SyncRequest / SyncPlan / TaskID / 执行结果，UI 仅订阅快照 | 最有利于多个 UI、后台同步、恢复任务及长期扩展 | 改动面最大；持久化、取消、依赖调度和 SDK 可变模型跨线程问题均需重新设计 | 有明确跨页面、后台或恢复需求后再实施 |

仅把全部代码挪进一个大型 `SyncDevicesViewModel`，实质上仍是方案 A 的职责状态，不建议作为重构完成标准。也不建议为 14 个 SyncType 各建一个控制器，重复维护同一套列表、停止和重试行为。

## 4. 推荐方案 B 的职责划分

以下名称为建议，不是已经存在的实现，也不要求一次新增所有类型。

| 组件 | 负责内容 | 边界 |
| --- | --- | --- |
| `SyncDevicesViewController` | 生命周期、导航、用户操作、激活提示、渲染与外部回调适配 | 不包含协议分支、发送循环和业务回写 |
| `SyncTaskPlanBuilder` | 将当前 SyncType 与上下文转成有序任务结构；管理现有场景构建器 | 复用 Node.getSyncData 和既有 planner；返回构建失败信息，由 UI 展示 HUD |
| 场景构建器 | 普通设备/Group、独立 Profile、Gateway Recovery、Emergency Fire、Battery Switch 等任务组装 | 只在业务规则确实独立时拆分；不为每个简单枚举分支建立类 |
| `SyncExecutionSession` | 当前轮次、任务选择、停止、重试、结束结果以及执行事件 | 统一会话状态所有权；通过窄接口调用现有发送组件和授权服务 |
| 专用策略 | 成功判断、ACK 超时、专用重试、补偿、动态追加消息和结果回写 | 先提取明确的独立规则，不构建大型通用插件框架 |
| 列表渲染适配层 | 展开、选中、进度、状态按钮、结构变更与可见 Cell 刷新 | 可以先是控制器内的小型辅助对象，避免过早增加 Presenter 层 |

过渡阶段可继续使用现有 `SyncDevices*Model`，保证消息创建时机与对象依赖不变。必须明确这仍是兼容阶段：不能把包含可变 Node/Handle 和 UI 状态的结构称为不可变纯业务计划。

最终由执行会话拥有任务运行状态，UI 持有展示状态并接收主线程事件或快照。若保留共享模型，应先明确串行访问规则；不能假设“加了一个 Session 类”就获得线程安全。

## 5. 分阶段实施建议

### 阶段 0：冻结兼容行为与验证入口

记录 14 类输入的关键任务顺序、依赖边、结果分类及特殊入口行为。保留当前暂存进度修复，作为 UI 刷新行为基线。

盘点硬编码控制器文件路径、方法名及源码片段的脚本，例如 `check_efc_controller_flows.sh`、`check_wifi_gateway_repair_recovery.sh`、`check_wifi_gateway_server_information_recovery.sh` 和 Group 的源码契约测试。移动代码时应同步迁移检查位置，不能直接删除或放宽断言来获得通过。

### 阶段 1：先抽离普通任务构建，再覆盖专用构建

从 `getSyncDeviceModel(...)` 和 Gateway Recovery 构建链开始，保留现有任务模型和消息生成时机，将输入上下文与输出显式化。随后缩减 `setupDataSource()`，让其主要负责分派构建与接收结果。

先搬迁再合并重复规则；Profile 的步骤依赖和任务依赖不同，不在同一轮盲目去重。构建错误通过结果返回，控制器继续负责 UI 提示和初始状态。

完成标准：输出操作、顺序、前置依赖和父级关联保持一致，Builder 不访问控制器或 UITableView。不能只是把 1,000 多行复制成另一个大文件。

### 阶段 2：抽离专用执行规则和结果汇总

优先提取成功判定、消防删除重试策略、失败任务重置与返回结果汇总。将 Battery Switch、Gateway、Daylight 的专用运行上下文从 UI 展开状态中分离。

迁出共用 Node Identify 方法时同步核对其所有调用方。重构不顺带修改协议、历史文案或无关资源。

### 阶段 3：抽离同步会话

将 `startSync()`、轮次 token、停止、调度和结束处理移入 Session。控制器发送开始/停止/重试意图并订阅事件。保留现有串行发送行为，注入可替换的发送与授权接口来测试成功、失败和取消。

重点验证旧回调到达、新一轮开始、等待中停止、动态追加消息及补偿动作的关系；一次性结束保护和清理归属必须明确。并发机制升级作为后续独立变更，不和机械迁移混在同一批。

### 阶段 4：视需要整理 UI 与领域模型

将结构刷新与进度刷新形成明确接口，保留当前 Cell 的连续动画与复用处理。若控制器此时仍难阅读，再提取列表适配对象。

需要后台同步、多入口共享计划等能力时，才继续推进方案 C，分离稳定任务 ID、运行结果与展示模型。

每个阶段独立交付和验证。不要为了把文件压到固定行数，强拆紧密相关的小方法；验收应看职责边界是否明确、业务规则是否可独立验证，以及新增场景是否还需修改主执行循环。

## 6. 重构必须保留的行为与验证

| 范围 | 必须验证 |
| --- | --- |
| 自动开始与重同步 | 默认进入后自动开始；`reSync: true` 等待用户操作；自动恢复最多两次附加重试及失败回调 |
| 任务顺序 | 删除/配置分区顺序；电池开关例外；Proxy 替换先删除后配置；初始化、入组、退组、TimeSet 和 Profile 前置关系 |
| 部分失败 | 成功任务保留；普通重试重新执行必要前置任务；Battery Switch 专用重置不能被普通规则覆盖 |
| 成功判定 | ACK 与本地业务状态检查；网关初始化、消防删除、电池开关专用规则；空消息的合法本地任务与必需消息缺失分开处理 |
| 动态消息 | 初始化补发基础配置、Daylight Recall 恢复消息的顺序、去重与最终结果归属 |
| STOP/退出 | 旧轮次回调隔离、PIR 恢复、Lux 解锁、Profile 快照补偿、消防部分清理状态保留 |
| 服务器任务 | 授权失败信息、后续任务依赖和验证阶段；授权 HTTP 成功不能替代设备配置完成 |
| 页面回调 | push/present；由调用方关闭和默认关闭两类路径；一次性 completion；不能重复 pop/dismiss |
| 进度 UI | 连续任务间隙、位数变化、展开切换、离屏返回、Group/Proxy 复用、失败和重试；保持进度更新不重建整表的行为 |

自动化验证优先覆盖真实业务规则：构建输出、选择下个任务、取消后迟到回调、局部失败重试、成功判断和回写次数。源码契约用于补充入口边界，不足以代替可执行行为测试。

现有 `scripts/check_sync_devices_progress.py` 提取生产进度方法并使用 UI 替身，可继续覆盖显示更新行为；它没有执行真实 UITableView 布局，也没有完整覆盖控制器结构刷新决策。

新增 Swift 文件必须加入实际使用的五个 target。后续按项目规则分别直接运行 generic iPhoneOS 的 xcodebuild，不使用 Simulator。若改到 UI 绑定、列表或约束，需按 AGENTS.md 做真实布局测试；Mesh ACK、设备状态收敛、服务器恢复另行验收。
