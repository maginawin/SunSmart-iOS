# 断网加载与 CPU 风险检查

## 结论

检查基于 HEAD `cf5e5c13`。不能保证未来不会出现类似性能缺陷；当前检查的前台恢复、云配置同步、Site 列表加载及两条时区同步路径中，未发现由断网失败直接驱动的无间隔无限重试。等待 HTTP 回调与主线程重复加载本地 Mesh 数据必须分别判断。

本次仅分析和执行隔离回归测试，没有修改业务代码。不是全项目无缺陷证明，也不是断网真机性能验收。

## 已有保护

| 路径 | 当前行为 |
| --- | --- |
| 前台／网络变化恢复 | `resumePendingSynchronizations` 在离线时直接返回；同账号和区域的进行中恢复合并；异步交接后复查网络和任务身份 |
| 云同步任务 | `CloudSynchronizationHandle.start` 离线时记录失败并返回；管理器移除失败任务，无失败后立即自我重试；等待定时器只触发一次 |
| 网关授权同步 | 循环仅在成功后发现新的待上传版本时继续；失败分支退出循环 |
| 普通 HTTP | API 请求超时默认 10 秒，网关删除／解绑全部为 30 秒；所查通用封装没有失败重试循环；编码和 JSON 解码使用后台队列 |
| Site 列表加载 | 仍会发起离线请求，回调先结束刷新；失败分支关闭 HUD，无自动重试调用 |
| 进入 Site 的时区同步 | 30 秒业务超时任务；取消和超时均结束等待，忽略过期结果对当前流程的影响 |
| 网关云时区状态轮询 | 每轮先异步等待 3 秒；总时限 60 秒；提交失败不启动轮询；状态查询失败可继续轮询，但受时限约束 |

请求超时配置不能直接理解为页面必定在该秒数内关闭：串行请求、收到响应后的本地导入，以及主线程阻塞都可能延长可见等待。业务超时任务也需要执行机会，不能打断正在主线程运行的同步计算。

## 剩余风险与证据边界

1. **大量待处理 Space 的重复本地工作。** 恢复筛选已跳过正常已同步项，但每个候选 Space 清理完成后仍调用 Site Zone 清理。分类器缓存只覆盖单次清理；K 个候选、Zone 成员引用 R 个 Space 时，该部分仍可能产生约 K × R 次读取入口调用。该复杂度来自调用关系推导，未测得此场景真机 CPU 数据。
2. **网络反复切换。** 恢复锁只合并进行中的同范围任务，没有跨完成轮次的冷却时间。多次恢复网络或前台事件仍能启动新一轮有限工作；是否造成明显负担取决于数据量、事件频率及运行耗时。
3. **有网络连接但服务器不可达。** 恢复入口只检查 `networkable`，后续仍可能先做本地准备再等待请求失败。完全离线时的入口短路不能代表所有弱网情形。
4. **加载界面的覆盖有限。** 本次检查了 Site 列表失败收尾和时区协调器；没有逐页审计全 App 所有 HUD，也没有证明所有异步路径都有统一总时限。

## 后续验证和防回归建议

- 真机分别检查：启动前断网、请求中断网、连上 Wi-Fi 但服务器不可达、反复断网恢复、大量待上传 Space 后回前台。
- 同时观察 CPU、页面触控响应、请求频率和加载提示是否退出；不要只看转圈或请求日志推断 CPU。
- 优先评估将恢复期间的 Site Zone 清理合并到每站一次，并增加大量待处理 Space 的读取次数回归测试；改动须保留清理和持久化安全语义。
- 对需要阻塞用户操作的多步骤加载流程，逐一确认总时限、取消和失败收尾；重复失败恢复可评估加入间隔。
