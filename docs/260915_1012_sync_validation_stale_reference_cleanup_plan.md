# 同步校验清理失效设备、Group 与 Profile 引用：修订方案

## 1. 修订目标与结论

根据用户本轮补充，将修复扩大为：**在同步准备与校验阶段，自动清理已经确认失效的设备引用、Group 引用及不再适用于当前 Group Profile 的配置，再按最新有效配置生成同步任务。**

本方案取代 [上一版方案](260915_1004_space_test_sync_failure_analysis_plan.md) 第 7～9 节；上一版的 Test Space 数据分析与根因结论仍有效。

本轮仍为重新分析、规划并请求确认，尚未修改业务代码、App 数据或服务器数据。

### 预期行为

- 用户点击同步后，可确认的历史残留自动清理并继续同步，不必逐条进入恢复弹窗。
- 不存在的设备不再生成重试任务，也不再因悬空引用阻塞整个 Space。
- 已不存在的 Group 不再作为配置目标；其现存设备需要执行的退订、解绑等操作仍正常完成。
- Group Profile 变更后，只保留当前 Profile 适用的数据和任务。真实待下发的新配置继续提示同步。
- 对无法完整读取、权限不足或有效配置版本冲突的情况，保留明确原因，不能把“未知”当作“不存在”。

## 2. 扩展分析：现有实现的缺口

### 2.1 已识别残留，但无法自动收敛

`ProximityLightingTopologyReconciler.normalize` 已能识别：

- 路径、Group Zone 中不再属于该组的设备地址。
- Space Zone 中不存在或已不适用的 Group/设备成员。
- 非 7/8 Profile 下残留的完整邻近照明路径。

但这些操作被统一认定为 destructive repair，普通导入、入口整理和导出会拒绝处理。人工引用修复还额外排除了完整路径清理。

此外，当前拓扑快照只有组成员地址与 `eligible` 等信息，不能完整区分设备已删除、移组、数据未加载、Profile 类型切换和配置版本变化。自动清理需要补充完整身份与来源信息，不能只移除现有 guard。

### 2.2 Group 不存在还涉及组归属和退订

`SpaceSnapshotExportIntegrityPolicy` 对本地和云端相同的悬空组归属返回 `allowVerifiedRemoteOrphans`，含义是保留该异常数据上传，并没有修复它。受保护的本地恢复导出还会拒绝这类快照。

设备退组链路使用 `.unsubscribeGroup(group: Group)`，消息构建和完成回调依赖 Group 对象。Group 已丢失时，单纯清理 Zone 不能解决节点悬空归属及旧订阅。

需要补充基于已确认旧组地址的清理任务和持久化记录，使不存在的 Group 不再成为执行前提。

### 2.3 Profile 变更不能只看是否支持邻近照明

- 7/8 → 1～6：旧邻近照明路径及相关 Zone 成员失效。
- 7 ↔ 8：仍支持邻近照明；有效路径和 Zone 应保留，白天/夜晚等 Profile 任务按新类型重新计算。
- 相同类型修改参数：保留拓扑，只废弃旧任务并按新参数重建。

现有 `GroupState` 不含完整 Profile 类型或版本。因此任务有效性还要关联 Profile 身份、类型和配置摘要，复用现有修订号或快照指纹，避免旧任务回调把新配置标成已同步。

### 2.4 Site Trigger Zone 也会受影响

Site Zone 成员校验要求节点存在、Group 一致，并且本地目标仍启用邻近照明。设备删除、Group 删除或 Profile 变为非邻近照明类型都会产生 `invalidMember`。

只修 Space 内路径，可能仍留下 Site Zone 同步失败。因此本次要把直接受影响的 Site Zone 成员纳入清理。Site 级数据仍走自己的持久化、权限和云同步流程，不能塞入 Space 上传载荷。

## 3. 统一清理规则

| 情况 | 自动清理内容 | 需要保留或继续执行的内容 |
| --- | --- | --- |
| 设备已不存在 | 路径中的对应位置置空；移除 Group/Space/Site Zone 的失效成员；移除指向该设备的场景、日程、传感器、代理等明确失效引用；剔除该设备旧任务 | 保留其他成员、路径槽位、Zone 身份和顺序；节点删除收尾以已有删除记录为准 |
| 设备已移至其他组 | 清理原组路径和 Zone 中不再有效的成员关系 | 保留节点和当前有效组归属；不按旧地址盲目替换新实例 |
| Group 已不存在 | 清理指向旧 Group 的 Zone、场景、日程、开关绑定目标及孤立扩展引用；废弃旧组配置任务 | 保留节点；现存设备上需要退订、解绑或删除旧配置的任务必须继续执行 |
| Profile 从 7/8 改为 1～6 | 清理该组不再适用的邻近照明路径、Group Zone 和 Space/Site Zone 成员；废弃旧 Profile 任务 | 保留组、当前 Profile 参数、节点及普通场景/日程；现存设备下发关闭旧功能及新 Profile 的必要任务 |
| Profile 在 7/8 之间切换 | 清理不再适用的旧类型任务，重算新类型目标 | 保留有效邻近照明路径、Zone 和成员；按新类型完成白天/夜晚等配置差异 |
| Profile 类型未变、参数已变 | 废弃旧参数生成的待执行任务与状态计算缓存 | 保留拓扑与有效逻辑配置，重新生成实际参数差异 |
| Profile 缺失或解码失败 | 不归入“Profile 已变更”清理 | 继续报告无法读取有效配置，不创建默认 Profile 覆盖原数据 |

补充约束：

- “设备不存在”以同一已确认数据版本中的完整节点列表及元素地址集合为准；离线、无信号、未扫描到均不代表不存在。
- “Group 不存在”以同一 Space 的完整组列表和引用身份为准。空 Group 仍然有效。
- 普通业务 Group、开关虚拟组、保留订阅地址分别识别；例如 FEFD 等有效特殊订阅不做通用组清理。
- Profile/扩展数据库行只有在确认没有任何有效引用时才能删除，避免删除被其他 Group 使用的配置。
- 清理是移除无效关系，不自动删除因此变空的场景、日程、开关或 Zone 等用户对象；无有效目标的对象不应产生失败任务。
- Site Zone 保留名称、ID、其他成员、未知扩展字段；是否满足最少成员等业务规则仍按现有逻辑处理。
- 正在删除但仍存在的节点，以及现存设备尚未完成的退组/解绑操作，不可直接清除其 pending 状态。

## 4. 数据来源与自动处理边界

### 4.1 先确定有效配置来源

统一校验使用同一账号、区域、Site、Space、Mesh 子网和恢复 generation 下的完整持久化快照，不能使用当前页面过滤后的列表或其他 Space 的全局 Mesh 对象。

- 本地正常编辑或用户已确认以本机恢复：以本地有效对象集合为准，保留待上传变更及删除意图。
- 云端完整配置通过版本和权限判断、确定应导入后：对该候选快照应用同一套引用清理规则，保留原始响应作为诊断和版本依据。
- 存在未完成导入、存储读取失败、对象身份不确定或有效配置冲突：先处理该状态，不推断缺失。
- 自动清理历史悬空引用不要求每一条都存在旧删除 journal；完整且已确认的数据来源可证明引用失效。journal 用于已有删除操作的收尾，不能根据悬空引用伪造硬件删除操作。

Test Space 已获得用户确认以本机列表恢复，继续保留 L2；云端旧 L1 不应被重新导入。本轮新增范围也适用于同一 Space 内其他可确认的失效引用。

### 4.2 区分可修复残留与其他错误

新策略返回清理计划、清理后的候选快照和未解决问题。只有列明规则且身份、类型、作用范围都确定的变更可以自动提交。

Profile 完整性错误、重复地址/归属、无法解码、有效配置容量超限、权限变化和云端有效配置冲突等问题继续保留。兼容旧 schema，但不能把损坏字段解释成空集合。

对本地/云端比较使用一致的清理规则，避免一边已清理、另一边旧残留导致循环阻塞；原始上传回执、配置版本和真正的有效字段差异仍保留原有校验语义。不能重写历史提交记录来制造同步成功。

## 5. 同步前统一执行流程

1. **准备快照**：核对身份、权限、数据来源、数据库读取完整性，以及导入/删除/上传恢复状态。
2. **生成清理计划**：覆盖节点、Group、Profile、相关 Zone 和任务引用，逐项记录清理依据及受影响现存设备。
3. **确认版本未变化**：提交前检查配置修订号、Profile 摘要、恢复 generation；变化则重新计算，不应用旧计划。
4. **持久化清理意图和备份**：使用现有 checkpoint、事务及恢复记录；涉及 App/Mesh 两套存储的操作需具备中断恢复与读回校验。
5. **提交逻辑清理**：只写计划中的失效引用，更新真实计数和云端待同步标记。
6. **完成已有删除收尾**：重放真实删除 journal，避免被同批历史残留再次卡住；完成读回后才标记 cleaned，成功上传后才确认对应记录。
7. **重新校验**：全部已知残留收敛后，清除由这些残留造成的配置阻塞和旧错误；其他未解决问题继续显示。
8. **重建任务**：剔除不存在对象及旧 Profile 的任务，为现存设备生成准确的退订、功能关闭、邻居更新及新 Profile 配置任务。
9. **分别确认结果**：云端上传成功更新云同步状态，设备命令成功更新设备状态，不能相互替代。

对于当前已因 `isBlocked` 被自动同步候选过滤掉的 Space，应允许它先进入“可修复残留”校验阶段。把清理仅放在导出末尾，会永远到不了该逻辑。

### 接入点

- Space 数据完整加载或导入完成后、首次同步状态重算前。
- 自动/手动云同步准备阶段，在阻塞过滤和普通导出之前。
- 设备同步的任务计划构建之前，以及重试重新规划时。
- Group 删除、设备删除、Profile 修改的现有保存流程，复用同一规则防止再次产生残留。
- Site Zone 同步准备阶段，处理与三类变更直接相关的成员。

`needSync` 等读取属性、UI 渲染和 DEBUG 导出保持只读；数据库清理由上述明确阶段执行。没有变更时不保存、不递增时间戳、不重复创建待上传记录。

## 6. Group 缺失时的设备收尾

这是比上一版新增的关键实现范围：

- 对仍存在的设备，记录旧组地址、设备 UUID/元素身份、需要取消的订阅/绑定及当前配置版本。
- 增加不依赖持久化 Group 对象的旧组地址清理能力，优先在 App 层复用 SDK 已有消息 API，不创建假 Group 恢复到业务列表。
- 如果设备确实还有旧订阅，保留退组待完成状态。退订成功后再转为无组状态；不能先把订阅观察缓存清空并标为成功。
- 云端载荷需保持组归属、退出待完成状态和订阅表示的一致性，不能改成无组状态却留下会触发预检异常的表示。
- 在线设备执行必要清理；离线设备保留真实待同步任务。配置结构不应因此继续被笼统报成“无效拓扑”。
- 旧回调必须匹配设备实例、旧组地址、当前任务版本，避免同一地址被重新使用后修改新设备或新 Group。

如果实现必须修改 SDK，已确认指定本地 SDK 工作目录存在；届时限定修改范围并验证全部引用 target。当前计划优先完成于 App 层，尚未修改 SDK。

## 7. Site Zone 与硬件观察状态

### Site Zone

对已确认缺失设备/Group、或 Profile 已不支持邻近照明的成员，更新对应 Site Zone 的目标成员列表，保留其他成员和字段，并走 `SiteTriggerZoneStore` / `SiteTriggerZoneCoordinator` 的版本、pending、云确认流程。

现有旧 schema 成员解析可能因节点已删除而整体失败，需要新增对“原始身份可辨认但目标已失效”的分类；不能先要求所有旧成员都能映射成现存 Node，才允许删除失效成员。

受影响的其他 Space 仍按自身权限和完整快照处理。没有权限或未加载的 Space 不能当作空 Space 清除；具体阻塞归于受影响的 Site Zone，不误清其他 Space 的成员。

### 硬件观察状态

本地拓扑清理只修改目标配置。节点的实际订阅、邻居、启用状态、Profile 回读值等观察缓存应继续作为设备任务的依据。

- 已不存在设备的任务直接移除。
- 仍存在设备的旧邻居需要按新拓扑更新；旧邻近照明功能需要关闭时真实下发命令。
- 同时存在 Space/Site Zone 配置时，先汇总剩余有效来源再计算目标，不能因为一条引用失效就关闭仍有效的其他功能。
- 正在执行的计划若引用对象或 Profile 版本改变，应停止使用旧计划并重新生成；旧回调不可确认新状态。

## 9. 已验证与实施后验证

### 本轮已完成

临时程序 `/tmp/space_sync_cleanup_scope_probe.swift` 编译并运行生产 `ProximityLightingTopologyPolicy` 与 `ProximityLightingTopologyReconciler`，确认：

- 缺失设备可以得到路径置空、Group Zone 和 Space Zone 成员清理结果，但现有策略会阻止自动应用。
- 缺失 Group 可以得到 Space Zone 成员清理结果，但现有策略仍会阻止自动应用。
- Profile 变为非邻近照明类型，可以得到路径与 Zone 成员清理结果，但现有恢复入口不接受。
- 有效邻近照明拓扑保持不变，清理后的再次归一化无新改动。
- 现存设备仍启用旧功能时，生产差异策略要求实际执行关闭命令。
- 本地/云端一致的悬空组归属目前被保留，并没有被清理。

以上是策略级隔离验证；完整的持久化、云同步和设备执行链路待实施后验证。

### 必须覆盖的回归

1. 原始 Test Space：保留 L2，清理 C00D 失效路径，删除收尾及云上传完成，旧云端不恢复 L1。
2. 不存在设备位于路径、Group/Space/Site Zone、场景、日程及同步任务中的各种组合。
3. Group 删除后留下 Zone 成员、节点组归属、订阅、场景/日程/开关目标；在线与离线设备分别验证。
4. Profile 7→1、8→1、7→8、8→7、同类型参数修改；有效数据保留，旧任务失效，新任务准确。

6. 空 Group、离线节点、特殊订阅、虚拟组、有效共享 Profile 不被误清理。
7. 地址重用、设备跨 Space 移动、旧任务回调、导入中断、读取失败、权限缺失和云端新版本冲突。

9. 反复校验无额外写入或时间戳增长，不产生新的永久待同步状态。
10. Site Zone 保留其他有效成员、未知字段及必要的跨 Space 收尾任务。
