# Timed 数量上限开放：测试用例规划

日期：2026-10-09。基准提交：`cf99bbd1c49666730da7af50dbeb43481e079c79`。分支：`feat/timed-limited-261008`。

状态：测试范围与用例草案，供确认后执行；所有用例均未执行。本文基于提交、当前源码及已有实施文档核对，不表示真机或服务端已经通过验证。

## 1. 结论与已确认范围

本次验证目标是：**同一个 Space 可以创建超过 16 条 Timed，每台支持定时的设备仍最多承载 16 条，旧数据升级和新旧 App 交替同步不造成丢失、覆盖或错误执行。**

用户已确认：

- 仅测试 iOS。旧 App 为上一发布版本，即未开放 Timed 上限的版本；执行时补录实际版本号和 Build。
- 一台手机固定安装旧 App，整个测试期间保留旧版本。
- 新 App 使用包含 `cf99bbd1c` 的测试包；若包含后续修复，记录实际提交和 Build。

已有实施方案确认的兼容规则：新版读取、迁移旧数据；采用新格式的 Space 可以要求旧 App 升级后再编辑，不要求旧 App 继续编辑新格式。**“旧 → 新可迁移”不等于“新 → 旧可无损编辑”。**

本规划以 SunSmart 完整测试为主，其他四品牌执行关键冒烟；这是建议的执行分配。服务端旧端门禁、格式防降级和并发保护是否部署尚未确认，使用固定旧版手机实测记录，不能预设这些保护已经生效。

## 2. 测试判定口径

| 项目 | 本次预期 |
| --- | --- |
| Space 数量 | 取消固定 16 条上限；32 条作为主要验收规模，不据此承诺无限规模性能 |
| 单设备数量 | Devices、Groups、Scenes 的不同定时合计最多 16 条；同一条定时作用于多台设备，各设备各占一条 |
| 停用和失败 | 停用、已保存但未下发成功、尚未确认清理的定时仍占容量 |
| 重复关系 | 同一条业务定时在同一设备只占一次；不同定时即使时间、动作相同仍分别计数 |
| 星期 | 一条定时选择多个星期仍只计一条 |
| 空目标 | 合法空组、仅关联空组的场景可以承载超过 16 条定时；之后加入设备时重新检查容量 |
| 编辑 | 设备已满时，允许编辑既有定时的名称、时间、动作及执行清理；不能因容量满而阻断恢复 |
| 本地升级 | 纯读取旧数据不应改变旧定时；涉及 Timed 的首次保存/预留可以触发格式迁移，不必等到第 17 条 |
| 新格式备份 | 新版可导入新版封装文件及合法旧文件；旧版不应把新版封装文件导入为可编辑 Space |
| 旧备份恢复 | 首次导入旧文件与旧安装升级应成功；用旧文件覆盖已经采用新格式的同一 Space 当前应拒绝，保留现有配置 |
| 云同步 | 上传成功提示之外，还需另一端读回完整数据；HTTP 成功、BLE ACK、列表条数相同均不能单独证明配置一致 |
| 真实执行 | 到时执行的设备、动作、星期和时间正确；未被选中的设备不得受到同编号槽位的误修改 |

本功能是 `Site → Space → Timed` 的 Schedule。Dongle Collection Schedule、网关的其他定时功能，以及尚未开放的 Rhythm/Time 不作为新增扩容对象。关联路径仅检查本次改动可能影响的行为，不展开无关功能全量回归。

## 3. 环境和数据准备

### 3.1 手机、账号与设备

| 代号 | 准备要求 |
| --- | --- |
| O：旧版手机 | 固定上一发布版本；保留本地配置和登录信息，用于旧云数据、旧文件、旧缓存及交替同步测试 |
| N：新版手机 | 使用新测试包；执行覆盖升级用例时，可先在 N 安装旧版并建立数据，再覆盖安装新版；不卸载，不影响 O 的固定旧版 |
| N2：第二个新版端 | 新版双端往返和并发用例需要额外手机；没有设备时列为受阻，不将 O 升级来替代 |
| 账号 | Owner、Editor、Visitor。相同账号双端读取和不同账号共享均覆盖；若环境限制同账号同时登录，记录限制并用授权共享验证，不宣称同账号场景通过 |
| A、B | 至少两台支持 Scheduler 的灯具，作为 A16+B16、不同空槽及错误覆盖检查对象 |
| C | 支持普通 Scheduler 与 Light LC Scheduler 的代表设备，用于 Auto/On、Off、组模式切换及清理验证；可由 A/B 兼任 |
| D | 无 Scheduler 的设备，优先有 Scene 能力，用于“不适用”边界；按实物能力选择，不凭产品名称推定 |
| 组/场景 | Manual 组、自动控制组、空组、含 A/B 的组、关联上述组的 Scene |
| 环境 | 专用测试 Site/Space；记录服务器环境、iOS、App Build、产品 PID、固件版本、组类型和 Site 时区 |

固定旧端 O 的测试数据可按用例恢复，但不改变其 App 版本。覆盖升级、清洁安装、权限变更是不同前置状态，应独立准备，不能用卸载重装替代覆盖升级。

### 3.2 建议准备的数据集

| 数据集 | 内容与用途 |
| --- | --- |
| L0 / L1 / L16 | 旧版创建并已上传的 0 / 1 / 16 条定时；L16 包含设备、组、场景、启用与停用组合 |
| L-local | 旧版尚未上传的新建 Site/Space，用于本地数据直接升级 |
| L-pending | 旧版保存后下发失败、删除失败或存在待上传修改；保留真实旧安装数据 |
| V32 | 新版同 Space：A 专属 16 条、B 专属 16 条，总计 32 条；名称和时间可明确区分 |
| V-mixed | A 上 8 条 Devices + 4 条 Groups + 4 条 Scenes；按实际适用设备去重计算 |
| V-hole | A/B 各有 15 条，A 仅槽 2 可用、B 仅槽 7 可用；先创建并确认清理对应定时，研发协助核对实际空槽 |
| V-pending | 新版含未下发成功、部分成功、待删除、待移出目标的定时，并保留另一台正常设备作为对照 |
| G-empty17 | 空组上 17 条定时；另准备场景仅关联空组的等价场景 |
| L-file / V-file | 旧版原始导出文件、新版超过 16 条的导出文件，均来自测试 Space |

数据集名称不代表必须准备同名文件。损坏数据、高业务 ID、指定 ACK 顺序等不能稳定从 UI 制造的情况由研发提供测试夹具，不让测试工程师猜测内部字段或修改业务数据库。

### 3.3 共用操作和证据

- 每条用例独立恢复前置状态；执行“保存 → 设备同步 → 退出重进 → 重启”时分别观察各阶段，不能只记录最后一次画面。
- 云端用例明确区分：手机联网但不连 Mesh、手机连 Mesh 但云请求失败、设备离线三种状态。测试上传失败时优先保持 BLE 正常。
- “配置一致”至少核对：总条数、名称、启用状态、Devices/Groups/Scenes 目标、时间、星期、动作及过渡时间；待清理配置还需检查重试后能收敛。
- 每设备槽位由研发协助读取/对照。业务 ID 可超过 15，设备物理槽位始终为 0～15；同一业务定时在 A/B 的槽位可以不同。
- 真实执行统一使用有效 Site 时区，选定当前测试日，时间预留配置耗时；先同步完成再等待触发。对“停用/删除不执行”的检查，安排同时间附近的正常定时作为时钟对照。
- 每个失败用例均记录恢复动作和重试结果，不以首次失败提示作为用例终点。
- 证据只保留必要页面、脱敏配置差异、请求结果和 DEBUG 片段；不将完整网络密钥、Device Key 或账号凭据写入报告。

## 5. 四条重点执行路线

以下路线将表格中的用例串成测试工程师可直接准备的连续场景；执行记录仍使用原用例 ID。

### 路线 A：固定旧版 O → 新版 N → 旧版 O

1. O 建立并上传 L16；记录 16 条的名称、目标、开关、时间、星期和动作。N 获取后仅查看，核对一致。
2. O 修改其中一条时间并上传；N 再进入，应看到更新。完成 SYNC-01。
3. N 创建只针对 B 的第 17 条并同步设备、上传云端；确认 A 的 16 条和 B 的 1 条都保留。
4. O 使用既有缓存重新联网进入。记录是否提示升级、是否能看到新数据、哪些操作仍能点击，不先假定保护存在。
5. 在专用 Space 中尝试 O 修改原定时并上传，以及修改其他会提交 Space 配置的入口；N 再次获取并核对第 17 条和全部原记录。
6. 预期旧端不能把新格式覆盖成旧格式。若 O 仍能操作或云数据被降级，保留完整操作顺序和脱敏差异，记 SYNC-03 失败/发布兼容缺口；不能只在 N 看到错误提示就认为云端保护通过。
7. 单独恢复一份仅 1～16 条但已迁移的数据重复步骤 4～6，完成 SYNC-02，避免只验证“超过 16 才拦”。

### 路线 B：保留旧安装升级 + 上传失败 + 重启

1. 在 N 安装旧版，建立并上传旧配置，保留该安装数据；覆盖安装新版。
2. 新版联网进入 Space，完成必要基线读取；保存首次 Timed 修改，使本地完成新格式迁移。
3. 保持 BLE 可用，让云上传失败；记录本地修改已保存、设备结果与云状态。
4. 退出并重启 N，重新进入；在云仍返回原已确认旧配置时，本地修改、数量和开关应保留，可正常进入。
5. 恢复云网络并同步；用另一个新版端核对完整数据和实际设备执行。覆盖 UPG-01/07、REC-05。
6. 另起独立数据，让旧端改变云内容或角色发生变化；不应再把这份不同响应当作原基线例外，覆盖 SYNC-10/07。

### 路线 C：待删除不释放 + 新版端接续清理

1. A 配满 16 条，删除一条时让 A 离线；记录失败和待删除状态。
2. 立即新增作用 A 的定时，应因未释放容量而拒绝；重启仍保持同样结果。
3. 将待处理配置上传，用 N2 获取，确认待清理信息仍在，不被上传/导入丢弃。
4. 恢复 A 在线并在 N2 重试清理；确认各 Scheduler Model 对应槽均无旧条目，任务已结束。
5. 再新增应成功；原定时不再执行，其他 15 条及 B 的配置不受影响。覆盖 REC-03、SYNC-12。

### 路线 D：新旧文件的四个方向

| 文件与接收端 | 操作结果 |
| --- | --- |
| O 导出的旧文件 → N 首次导入 | 成功，旧配置可迁移 |
| N 导出的新版文件 → N2 | 成功，超过 16 条及设备绑定完整 |
| N 导出的新版文件 → O | 拒绝作为可编辑 Space 导入，原数据保留 |
| 先前旧文件 → N 已升级的同一 Space | 拒绝覆盖，保留 N 的新配置 |

导入提示成功后仍需退出重进、重启并检查实际配置；拒绝时不得新增残缺 Space 或清空原 Timed。

## 7. 执行顺序与结束标准

建议顺序：环境/数据准备 → CAP-01/02/03/10 冒烟 → 旧安装升级 → 新旧端同步及文件 → 失败恢复与组/场景 → 权限/品牌 → 研发专项和并发联调。

采用三层结果分别交付：

1. **App 配置与设备层**：保存、容量、持久化、清理、重试、读回及实际定时执行分别有结果。
2. **云端往返层**：另一端完整读回，重启后仍一致；上传接受但尚未核实的状态不记同步成功。
3. **混合版本发布层**：旧端在线写入保护、格式防降级、并发保护实测通过；旧版离线 BLE 风险有明确发布约束。没有该证据时仅能报告 App 已测范围，不能宣布混合版本上线安全。

P0 全部通过、P1 有明确结果或经确认的遗留项后，才形成对应范围验收结论。发现丢数据、错改其他设备/定时、提前复用槽位、旧数据覆盖新版、失败后不能恢复，均作为阻断项处理。外部配套未完成只阻断对应发布验收，其他可执行 App 用例继续。

业务断言已满足后结束对应验证，不将本功能扩成所有品牌、所有固件、所有权限的全排列；设备/品牌缺口按实际记录。
