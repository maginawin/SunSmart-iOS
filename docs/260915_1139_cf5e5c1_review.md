## 历史证据与原因

通过 `git show`、父版本 `git blame` 及 `git log -S` 交叉确认，以下三部分全部首次出现在 `54804a09`：

1. 父版本 `CloudSynchronizationManager.swift` 第 392–395 行，在前台/网络恢复流程中，对所有没有云同步任务的 Space 调用 `SpaceSyncCleanupCoordinator.prepare`，没有先检查是否存在待处理状态。
2. `SpaceSyncCleanupCoordinator.swift` 第 94–95 行，每个 Space 清理成功后都调用 `SiteTriggerZoneCoordinator.cleanObsoleteMembers`；正常路径还包含清理前导出与持久化读回导出。
3. 父版本 `SiteTriggerZoneTopologyReader.swift` 第 93–104 行，`cleanupClassifier` 创建时就遍历整站可编辑且未受阻的 Space，加载 Mesh、Group 与拓扑，而不是根据实际 Zone 成员按需加载。即使没有成员，也先付出了整站加载成本。

同一 Site 有 N 个可清理 Space 时，上述嵌套路径可造成近似 N² 次 Mesh inventory 构建；恢复任务及清理协调器运行于 MainActor，因此大量有限扫描即可造成持续主线程繁忙，不需要存在无限循环。`54804a09` 的父版本尚无这段恢复清理循环，也没有该分类器。

## 对修复的检查

- 恢复只选择待上传、有未确认上传或受阻的 Space，跳过正常已同步项及已有同步任务。
- 候选之间交还主队列，并在恢复后重新检查账号、区域、网络及同步任务状态。
- 分类器按合法成员的 Space ID 延迟加载；单次操作缓存成功与失败读取，保留未知成员，不授权删除无法确认的引用。
- 正式云同步入口以及进入 Space 的 `reconcileLegacyProximityLightingTopology` 仍调用完整清理；跳过历史无标记配置的前台检查是补丁明确说明的行为调整，并非误删清理入口。
- 没有修改 SDK、资源、本地化、品牌 target 配置或 UI 布局。
