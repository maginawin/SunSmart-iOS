日期：2026-10-29；状态更新：2026-10-30。Q01～Q10 和 R1～R5 已确认并同步需求和测试预期。App 实现与自动验证已完成，最新阶段、提交与验证状态以[开发方案与执行计划](261029_1922_device_scene_development_plan.md)第 7 节为准；真实界面、设备及云端验收仍待执行。

本轮已同步修订需求正文、UI 差异和测试预期，不仅追加回答。用户本轮确认优先于旧原型；“代码核实”表示为落实“复用现有机制”而查到的实际行为，“建议补充”仍不是用户已确认规则。本文保留需求与验收口径；后续开发方案、文件级任务和执行记录见[开发方案与执行计划](261029_1922_device_scene_development_plan.md)。

## 1. 结论

本需求可以在现有 App 上实现。现有代码已具备单设备开关、调光、调色温，以及把灯的状态保存为场景、再次执行场景的基础能力。主要新增工作是：让用户选择具体设备、为每台设备保存独立参数，并把这些设置接入保存、重试、同步、分享和删除流程。

这不是只增加一个 Devices 页面的小改动。当前场景主要按组管理；如果只改页面，后续组同步、定时或设备恢复仍可能漏掉设备，或者把独立参数覆盖成组参数。

**用户已确认：Groups 与 Devices 互斥，一个场景只采用其中一种方式。Devices 页中的 Group 只是把设备分类展示，方便查看和批量操作，不是“组与设备混合加入场景”。**

建议沿用现有场景编号、设备控制、同步和容量检查机制，补充逐设备的配置记录。现阶段没有证据表明必须增加固件命令或新服务器接口，但设备能否正确记住并恢复状态、云端能否完整保留新增配置，仍需联调确认。

## 3. 用户要完成什么

用户希望从同一 Space 中挑选若干设备，为它们设置不同的状态，并通过一个场景一起调用。例如：同组中的灯 A 为 30%、灯 B 为 80%，另一组的继电器关闭，未分组的色温灯为 4500K。没有选中的设备不应被修改。

| 场景方式 | 加入场景的对象 | 参数如何设置 | 组成员变化的含义 |
| --- | --- | --- | --- |
| Groups：组场景 | 组 | 按现有组场景规则设置 | 沿用现有组场景同步规则 |
| Devices：设备场景 | 用户明确选中的设备 | 每台设备独立设置，也可批量填写 | 显示分组不产生成员关系；新加入该组的设备不会自动加入此场景 |

本次保留现有组场景、自定义名称、图标和模板入口。不把 RGB、渐变、动态灯效或每个输出通道独立编排自动纳入范围。原型没有给出这些需求。

## 4. 页面和操作要求

### 4.1 场景列表与创建

**原型明确**：从 Scene 列表新增，进入 Create Scene，保留 Custom、Templates、名称和图标选择。点击 CREATE 后进入 Settings，可看到 Groups 和 Devices。

**用户确认**：两种方式互斥。创建时选择 Devices 后，后续编辑和保存应按设备场景处理，不能同时保留一份会生效的组场景配置。

**建议补充**：名称的空值、重复名称和长度限制沿用现有校验；选择方式和设备参数尚未完成时，不应在正式列表留下一个可执行的空设备场景。当前创建代码会先创建场景再选组，设备场景需要调整这一时序，或可靠清理未完成记录。

原型列表里的 `8/16` 不能照搬为 Space 上限。当前分支已改为显示场景数量，并按目标设备检查容量。设备场景也应使用同一规则。

### 4.2 组场景搜索

**原型明确**：Groups 页新增 Search groups；输入部分名称即可显示匹配结果，示例输入 `5` 后显示 Group 5。

**建议补充**：清空搜索恢复全部组；搜索和取消搜索不清除原来的选择或参数。无匹配结果时给出空结果说明。大小写和空格处理沿用项目现有搜索习惯。

### 4.3 设备场景入口与选择

**原型明确**：Devices 初始页提供 SELECT DEVICES，并说明“设备场景不能提前空建，至少需要一台设备，只有在线设备可以添加”。

选择页包含 Search devices、已选总数、Not in group 和各个 Group 分类。分类可展开查看设备和已选数量，支持名称模糊搜索；原型输入 `pan` 后保留匹配的 Panel 设备及所属分类。空组显示 `0/0 selected`。

**建议补充**：

- 选择仅限当前 Space 内的有效设备。还要满足场景保存能力，不能只凭“在线”就允许加入。
- 已有场景中的设备离线后仍需显示，保留原配置并标明离线；“不能新添加”不等于“自动从场景删除”。
- 搜索只改变显示结果，不改变选中集合。已选总数按实际设备去重，分组标题不是另一个场景成员。
- 设备取消选择与已保存成员移除应区分：尚未写入设备的草稿取消，不应被无关设备的离线状态阻断。
- 早期原型中的眼睛图标含义不明确；本轮 UI 图层已标为 Identify Device（定位设备）。定位沿用 Q03 的既有能力判断和发送机制，具体型号反馈由实灯验收，不再作为未决产品规则。

### 4.4 单设备参数设置

| 设备类型 | 原型展示的设置 | 补充要求 |
| --- | --- | --- |
| Relay 继电器 | ON / OFF | 不出现无效的亮度和色温控件 |
| 单色调光灯 | 开关、亮度 | 采用设备实际允许的亮度范围 |
| 可调色温灯 | 开关、亮度、色温 | 采用设备实际支持的色温范围 |

**早期原型明确**：参数窗口有 CANCEL 和 APPLY；设备行展示保存到草稿的摘要，例如 `100% · 4500K`、`100%` 或 `ON`。最终 UI 的调光和色温层没有这两个可见按钮，继电器层仍有；最终提交/放弃方式以 U03、Q02 的确认结果为准。

**按用户要求复用，并已核实代码**：调光/色温/批量弹层中的拖动、加减、OFF 只更新弹层数值；点遮罩提交到编辑草稿，不立即控制灯。继电器 APPLY 对齐此边界：更新草稿，CANCEL 放弃弹层修改。预览和正式同步才发送命令。

现有组场景新参数默认 ON、100%、4500K，并按允许的亮度上限和有效色温范围调整；OFF 后再次打开采用允许的最大亮度，不是自动恢复上次值。已有场景回显已保存参数。设备场景沿用这些机制，但范围必须来自具体目标设备，不能因展示在某个分类就继承整组场景绑定。继电器只保留 ON/OFF；批量设置只处理各设备支持的字段，色温沿用逐设备范围修正。亮度应沿用既有 trim/显示换算，不另造转换或静默改变已有组场景语义。

开关与亮度 0 的关系要统一，避免摘要显示 ON、实际却发送关灯。应复用已有处理，并补查继电器没有亮度字段时的判断。

### 4.5 按显示分类批量设置

**早期原型明确**：Not in group 和各 Group 标题提供批量设置入口，窗口包含开关、亮度、色温以及 CANCEL / APPLY。最终 UI 保留参数控件，但没有可见 CANCEL / APPLY；按 U03、Q02 确定关闭时的行为。

**用户确认所带来的要求**：这里只修改该分类下已经选中的设备。例如 Group 1 有十台灯，场景只选择两台，批量操作只影响这两台，不能向整个 Group 发送控制而连带改变其他八台。

**复用规则**：混合类型批量设置只将设备支持的参数应用给它：继电器只处理开关，调光灯处理开关和亮度，色温灯再处理色温。使用现有有效能力、范围限制和换算；批量设置后允许再修改单台设备。复用的是参数机制，不是向真实组发送命令。

### 4.6 已选设备页与移除

**原型明确**：选择完成后展示 Selected devices (N)，按分类显示设备和参数，提供重新选择、参数调整、移除及预览入口。分类和设备行都有移除图标。

“分类移除”就是点分类标题旁的删除按钮，批量从场景移除该分类下已经选中的设备。例如 Group 1 中 A、B、X 三台设备，只有 A、B 在此场景内，则移除目标只有 A、B。它不删除真实组，不删除设备，也不影响其他场景。

**用户已确认**：离线依据设备状态判断；已有离线成员可以保存和单台移除。任务下发失败时保留需要同步的状态。移除应记录“需要从设备清理此场景”，不能仅删除本地记录，也不能在设备未确认清理时释放物理占用。

**用户已确认**：分类移除按单台移除的批量版本处理，同样允许离线成员产生待清理任务；确认弹窗明确列出数量和离线待同步说明。不再沿用旧原型的“分类中有离线设备就不能移除”。

编辑阶段移除先改变草稿，最终确认保存后再提交清理意图；未确认前放弃不改变原配置。这是按 Q07 草稿规则落实的时序，并非声称用户单独指定过清理命令的启动节点。提交后失败或重启保留待清理任务，后续设备同步继续；需要处理关联定时的目标按现有依赖顺序清理。重新加入同一设备时，必须撤销旧的待清理意图，避免迟到删除把新设置清掉。

### 4.7 预览

**原型明确**：建议用户预览，但不强制先预览。点击预览后，把当前设置发给全部已选设备，显示 Applying preview；完成后提示用户检查所有实灯。

预览确实会改变灯的状态，但不等于设备已记住场景。预览完成后仍留在编辑页，可继续修改。修改选择或参数后，之前的预览不能代表当前草稿已经检查过。

**建议补充**：发送期间防止重复启动和同时修改同一草稿；失败时说明哪些设备没有完成，并保留编辑内容供重试。连接到 Mesh 网络不代表每台设备都可达，不能只检查蓝牙连接后就显示全部成功。

### 4.8 DONE、现场确认与保存

**保留原型步骤，按本轮离线与待同步规则更新结果说明**：

1. 点击 DONE，提示保存前将当前设置发送给设备，可选 CANCEL 或 SEND。
2. 点击 SEND 后显示发送进度，提示保持页面打开。
3. 发送结束后检查可达设备的实际状态，同时列出失败、离线及仍需同步的目标；不能要求用户确认离线目标已经成功。
4. 选择 ADJUST AGAIN 返回调整；选择 CONFIRM & SAVE 进入保存。

即使此前已经预览，DONE 仍要重新发送；没有预览也可直接走此流程。最终确认必须针对本次发送的同一份设置。

**本轮确认后的保存与同步规则**：

- 保存用户的期望配置，与设备是否全部写入成功分开。已有离线成员不阻止保存；发送/写入失败的设备保留同步任务，整个场景显示需要同步。
- 未提交的预览修改仍是草稿。预览失败可以显示结果并重试，但不能生成放弃编辑后仍会执行的正式保存任务；否则会与 Q07“未提交草稿不跨重启保留”冲突。
- 保留原型的 DONE 再发送与最终确认步骤。为兼容离线保存，建议确认页列出已发送设备、失败/离线设备和“确认保存后仍有待同步任务”，替换“必须每一台实灯都正确才能保存”的绝对表述。这里确认的是期望设置和未完成清单，不是让用户假认离线设备成功。
- 最终确认后持久保存期望配置和未完成任务；需要写入的设备按既有场景同步机制执行，成功一台更新一台，失败不丢任务。参数已发出、设备已写入、App 配置已保存和云端已同步分别表达。
- 已确认任务中断后由设备同步继续，不重复创建场景。正常重试复用现有同步机制，不要求每次再走创建页面的现场确认；仍须复核当前设备身份、期望值、权限、容量和命令结果。
- 场景待同步期间，设备可能执行到不同版本；不能声称一次保存会把全部设备一起切换。设备场景首期接入现有定时和实体开关；列表和相关选择入口显示待同步状态，不单独因为待同步而禁止选择或调用。仍沿用权限、连接及能力限制；不能只禁用 App 按钮就声称实体开关或设备内定时不会触发。
- 已有目标同编号编辑和减少成员可保存待同步；真正新增占用、明确超额、身份或权限错误不因“支持离线”而放宽。设备真实写入前仍需检查实际占用。现有组场景页面的全局连接检查和部分预读逻辑并不完全满足此规则，不能整页照搬。

### 4.9 取消和退出

**原型明确**：取消编辑时弹出 Discard scene settings?，可选 KEEP EDITING 或 DISCARD；放弃后不保存本次选择和参数变化。

**用户已确认**：放弃编辑不恢复已经改变的实灯，不保存本次未提交草稿；未提交草稿不跨重启保留。应在文案中区分“放弃设置”和“恢复灯光”。放弃编辑不会删除以前已保存的场景。

最终确认后中断的任务属于未同步任务，记录须保留，后续通过设备同步继续。未提交、已提交待同步、已同步三种状态不能混淆。页面退出和迟到回调不得把已放弃的草稿重新提交。

### 4.10 查看、编辑和执行

**原型明确**：长按场景进入详情，显示 Device scene · N devices，按分类展示各设备参数。更多菜单保留 Edit、Delete、Settings；Settings 返回类似创建时的设备设置页。该编辑页未展示 Groups / Devices 切换栏。

**结合现有行为的建议**：Edit 沿用修改名称和图标；Settings 修改设备及参数。点击列表场景继续执行已有场景。执行时每台已选设备恢复自己的值，未选设备不应因为同组而被控制。详情展示保存的参数，不伪装为实时读取值。

**用户已确认**：有成员的已保存场景首期不转换类型；空场景允许切换 Groups / Devices，这是“已有场景不转换”的例外。只有无有效成员且无待清理任务，才允许切换；有待清理任务时提示用户先完成清理，不能只看列表为空。

## 5. 关联规则：必须随功能一起成立

| 事项 | 要求或建议 | 原因 |
| --- | --- | --- |
| 权限 | 沿用 Space 的场景操作权限；访客不新增、修改或删除。配置受保护、正在退出 Space 等状态继续遵守现有约束 | 新入口不能绕开已有权限 |
| 紧急状态 | 预览、发送参数及执行场景按实际设备检查现有紧急控制限制 | 只检查显示组会漏掉未分组设备 |
| 设备换组 | 已确认：换组、退组和后续组成员变化不改变设备场景成员及参数，仅更新显示分类 | 成员是明确选择的设备，不是分类标题 |
| 真正删除设备 | 清理它的直接成员关系和待同步任务；删除后重新配网不得仅凭地址或名称自动继承 | 防止新设备误用旧设备配置 |
| 同一设备多场景 | 可参加多个场景，但每次新增都检查该设备的实际可用容量；编辑同一场景不重复占位 | Space 场景总数与单设备容量不同 |
| 定时调用 | 已确认首期接入；仅对选中的设备安排任务，增减成员同时更新相关定时并检查容量；显示待同步状态，不仅因待同步禁止选择或调用 | 不能把整个显示分类加入定时 |
| 开关调用 | 已确认首期接入现有实体开关入口，显示待同步状态，不仅因待同步禁止选择或调用；跨组触发范围须核对实际开关发送目标并实机验证 | App 能执行不代表所有开关都能跨组执行 |
| 整体删除 | 检查定时和开关引用；完成设备清理后再释放场景编号，失败保留可重试状态 | 防止旧灯响应复用后的同一编号 |
| 分享、换手机和恢复 | 已确认：未完成配置可分享，接收后仍显示待同步，由进入 Space 的 editor 继续处理 | 必须保存期望参数、待写入/待清理目标，不能只传设备执行缓存 |
| 旧版本 | 本期声明旧 App 不支持设备场景，不保证技术拦截，不新增云分享等版本保护；已明确接受旧版访问或上传造成字段丢失的风险 | 新版规则不能自动约束已经发布的旧客户端 |
| 品牌和文案 | 共享逻辑影响五个品牌；新增可见文案补齐 English 与简体中文，复用已有组件和资源 | 原型只画一个品牌不代表代码只影响一个 target |

换组规则已经明确，不再列为待确认。移除最后一台可以形成无有效成员的状态；空场景可切换类型，但存在未完成物理清理时必须先提示并完成清理。新建设备场景仍沿用至少选择一台的原型要求，不把“空场景可切换”自动理解成“可直接创建并执行空设备场景”。

| 容量和删除 | 当前分支已有读取设备占用、容量预检、删除确认 | 把直接设备成员和待清理目标纳入同一机制 | 可扩展现有机制，不需另建一套编号体系 |

| 本地和云数据 | 现有本地存储及导入导出流程 | 类型、直接成员和参数贯穿完整数据链；旧版本风险按本期不加保护的决定记录 | App 可开发，云端字段往返需验证 |

具体来说，当前 `SceneInfo.groups` 根据组的场景参数反查成员；节点的 `sceneExecuteDatas` 是设备执行后的缓存。前者不能表达独立设备成员，后者也不能表达“已经选择但还未成功写入灯”的状态。

现有 `getSyncMessageHandles(node:data:)` 会在参数命令后直接加入 Scene Store，不能原样用于确认前预览。与此同时，Scene Store 回执、Scene Recall 回执、列表点击后的状态更新和组同步路径，都存在对组参数的依赖。这些必须一起适配。

## 7. 推荐实现方向及外部配合

推荐在现有场景体系内增加明确的场景类型和逐设备配置。名称、图标、编号、容量检查、同步执行和删除流程继续复用；所有需要知道场景成员的地方，从统一规则取得实际设备和参数。

不建议把每台设备包装成一个隐藏组：这会改变真实组关系、占用组资源，也容易影响其他组功能。不建议直接拿设备执行缓存当配置：失败和重启后无法区分“用户想保存的内容”与“灯已经保存的结果”。这是技术建议，尚未进入实施方案审批。

按实施依赖建议分三部分：

1. 先定义并打通数据：场景类型、设备身份、参数、未完成状态、本地和导入导出兼容。
2. 再打通行为：选择、批量设置、预览、二次发送、确认保存、失败重试、同步及删除。
3. 最后完成关联验收：定时、开关、换组恢复、容量、云端往返、旧版本和品牌适配。

| 配合方 | 需要确认的事项 | 验收方式与发布依赖 |
| --- | --- | --- |
| App 团队 | 新配置写入本地、导出、导入和分享后不丢失；权限与失败状态一致 | 新建后重启、换手机恢复和失败重试；属于本次必须完成的 App 工作 |
| SDK | 复用参数设置、Store / Recall、占用读取和回执；是否新增 API 在详细设计时确定 | 当前 SDK 有基础能力，但尚未证明无需任何 SDK 改动；如新增 API，正式依赖发布后才能交付 |
| 固件团队 | 各目标型号是否能存储并恢复所需的开关、亮度、色温；继电器及多输出设备是否一致 | 保存、断电重启、执行场景并观察实灯；只读分析和联调，不在本任务修改固件 |
| 服务端团队 | 上传配置是否完整保留新增的类型、设备成员和参数；下载、分享、转移是否原样返回 | 上传后重新下载并比较，再由另一手机恢复；如需要接口或存储修改，由服务端团队实施并明确发布顺序 |

目前只能判断为“App 有实现基础，完整功能有条件可行”。未核对服务器实际存储行为，不能承诺不需要服务端配合；也不能仅依据设备支持普通控制就承诺支持所有场景保存内容。

### 10.3 现有机制可复用，但不能直接照搬的地方

**本轮新增范围：组场景与设备场景统一保存交互，共用保存、任务生成、失败状态、重试和恢复规则。** 不建立两套平行同步机制；必要差异仅是目标来源：组场景跟随组成员，设备场景使用明确选中的固定设备集合。组模板、自定义创建和已有场景编辑均需纳入关联检查，不只改一个保存按钮。共享改动覆盖现有使用这些入口的品牌和 Space，按已有功能可见性执行，不另增品牌开关或扩展独立多通道编排；这些由代码核对和验证完成，不要求用户重新列举。

组场景已支持无实际设备的空组预配置，应继续保留；不能把设备场景“至少选一台在线设备”的新建规则套到组场景。无实际设备也不等于没有已配置的组成员关系，不能把绑定空组的组场景直接当作可无损转换类型的空场景。按已确认 R5，有实际设备目标时统一使用发送设置及结果确认流程；合法空组预配置直接保存。

- **离线编辑**：容量底层已允许同编号修改和减少关系；但现有组场景保存页仍有全局 Mesh 连接检查，并可能预读未知定时状态。两种场景都要满足已确认的离线保存规则，不能复用这些拦截后又称已支持离线。
- **新增关系**：新增设备仍需在线且能力满足。新增场景占用或新定时目标继续执行既有容量预检；不把已确认超额、权限错误当普通通信失败。既有成员从未成功写入时，业务上可待同步，但真正写入前仍核对物理占用。
- **移除**：保存期望移除不等于灯已删除；保留原设备身份、场景编号及相关定时清理状态。未确认清理不释放容量/编号，重新加入必须撤销过期清理。
- **分享未完成任务**：分享的是可持久的业务意图和待处理目标，不是运行中的队列、闭包、超时计时器。换手机后可按当前期望重新生成任务，未知设备占用按正常读取流程确认。进入 Space 的 editor 仍需符合已有编辑权和配置保护机制。
- **旧版**：现有定时 v2 的格式/降级保护只保护该格式，不证明其他旧版能拒绝设备场景。没有足够证据时，不用服务端或固件改动替代 App 范围内的需求决策。

本轮仅更新分析、规则和测试用例，不改 UI 设计源文件、不改业务代码、不执行固件或服务器变更。

- 实际改动与偏差：完成了什么；与计划不同的地方、原因及已确认的范围变化。未做部分和后续动作单列。
- 验证证据：对应 DS 用例、自动化测试和构建结果、必要设备与通信条件。自动化、构建、真实设备和云端结果分别记录；未执行不能写通过。
- 可复核的代码状态：执行工作树、分支、HEAD 及相关未提交差异；涉及 SDK 时写明实际来源、revision/未提交差异和发布待办。记录事实，不因交接自动提交或推送。

执行 session 每完成一项就更新记录，结束时在同一计划中补充简短交接摘要：已完成、未完成、风险及下一步。详细日志或设备验收证据较多时，可以另存附件并从计划链接；不复制一整份任务清单，避免两处状态冲突。

执行 session 必须显式读取本文、Figma 链接及最终计划，不能假设它继承本会话的聊天记录。同一工作树的文档同一时间只由一个会话写；不同工作树先确认拿到相同版本的文档，结束后明确返回哪个路径及代码版本。当前本文尚未提交，另一个工作树不会自动拥有它。当前会话后续复核时，以实际代码差异和验证证据为准，不把“已打勾”直接当作验收通过。
