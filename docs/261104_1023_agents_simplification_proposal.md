## 6. 重点条款的建议表述

以下是供评审的替换方向，不是已写入生效的规则。

**授权与阶段执行：**

> 分析、方案和 review 只交付分析。实施按本会话最新授权的范围推进，沿用已确认决定和原计划，不重新讨论已解决问题；只对会改变需求、兼容性、实施方向或授权边界的新问题确认。用户指定分阶段时完成该阶段及必要验证后停止。

**Superpowers 与子代理：**

> 仅在用户指定时使用 Superpowers，并按当前任务选用所需步骤；指定分析不扩大为实施，指定执行已有计划不重开需求讨论。子代理只用于独立且能节省时间的任务，通常最多两个、默认只读；按实际风险安排审查，不把每个阶段都扩展为一套新流程。

这条调整的是本项目调用流程的范围，不修改插件技能本身。历史多代理实施有明确授权（E2/E3），不应将其描述为自动越权。

**分析与复杂度：**

> 从直接证据沿实际调用、共享数据和状态依赖扩展，覆盖会改变结论的上下游与同类入口。优先复用现有机制；必要新增持久状态、恢复流程或独立协调机制时，在方案中简述现有机制为何不足及新增维护成本。能解释触发链、关联影响和验证边界后结束扩展，不因分析覆盖广而自动扩大实现。

**状态与保护：**

> 修改同步、删除、恢复或完整性保护时，同时验证应拒绝与应允许的场景，以及存量状态的恢复路径。检查本次内存变更、保存/规范化、重载与任务生成是否连续，避免操作创建的状态阻断自己的后续步骤；新增用户操作限制须在方案中说明行为变化，不能仅称为“加强保护”。

**测试与运行证据：**

> 按本次风险选择已有回归；夹具若绕过实际序列化、持久化或异步边界，补充最小行为复现或明确未覆盖路径。相关检查通过后停止扩大验证；构建、离线回归和设备/云端运行分别报告，不能互相替代。

**同步工作量：**

> 调整设备同步任务时核对变更目标、已成功状态及历史待重试任务；避免对未变化且已成功的目标重复生成任务。优化耗时或控制体验时，说明实际目的地址、命令次数、ACK/UNACK 和重试变化，以现场命令/trace 验证效果。

这条应并入项目现有同步/性能要求，不独立扩展为所有任务都要提交命令统计表；E5 是其触发示例。

**协议文档：**

> 面向执行方的文档按执行顺序写清触发条件、具体目标（Element、Model、目的地址）、命令和参数值/单位、ACK 与失败重试。决定范围的术语附可执行判断和最小例子；区分标准、当前 App/SDK 行为及设备实测，只补充影响执行的背景。

**Git 与跨工作树操作：**

> 未明确授权时不 commit、push、merge 或同步其他工作树；已有授权在当前范围内持续有效。需要发布规则更新时，先核对目标工作树状态，再按用户指定范围独立提交/同步。

## 7. 实施顺序与验收

确认后只改两份 AGENTS.md；不修改业务代码、SDK、插件、记忆、构建配置或其他工作树。

1. 按上述职责归属移动和合并条款，先去重，不弱化约束。
2. 对授权/阶段、复杂度、真实状态边界、Git 同步四处补齐可执行表述；其余优先改写现有条款。
3. 用下表检查行为是否仍明确。然后检查 diff、重复条款、路径和命令，不运行 App 构建。
4. 在新会话核对实际加载的两层规则；用后续真实任务观察效果，不以字节减少直接宣称更快或更省 token。

| 代表场景 | 精简后仍应产生的行为 |
|---|---|
| “分析原因，规划方案与我确认” | 覆盖必要关联入口，交付方案；不改业务代码 |
| “按已确认计划做 T03～T04” | 核对当前状态及接口，只完成授权阶段，不重开整轮讨论 |
| 单个布局或文案修复 | 复用组件，做相关检查；涉及 Swift 生产代码按项目要求构建，不自动真机、不新增完整流程 |
| 删除最后设备、缺字段或空 Scene 配置 | 同时验证合法允许路径、真实异常拒绝路径和失败恢复，不整体放宽身份/权限检查 |
| 状态机/持久化修改 | 最小夹具经过相关真实边界，覆盖本次操作是否阻断自身后续任务 |
| 多品牌资源或 SDK API 改动 | 按受影响品牌与正式依赖可用性验证，不把单品牌本地构建当完整交付 |
| 性能修复 | 使用现有 trace 和同条件复测，自动化通过与实际改善分开 |
| 用户说“我自己测” | 继续完成 App 与自动化工作，列最短人工步骤，不再要求解锁或连接设备 |
| 外部数据异常 | 只读分析契约和返回，交给外部团队实施，不修改/部署后端或固件 |
| “调整这份规则” | 只改指定文件，不自动提交、推送或同步其他工作树 |

编辑目标：全局约 18～22 条、项目约 28～34 条，合计约 10～12 KiB。若为了达到数字必须牺牲具体授权或兼容约束，则保留条款，不追求压缩指标。
