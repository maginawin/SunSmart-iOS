# P1：首次全空间拓扑主线程阻塞修复计划

## 1. 目标与实施范围

依据 [1a55fe7 核查](260915_1802_commit_1a55fe7_p1_analysis.md) 和 [原 R3 方案](260915_1728_ipad_performance_optimization_plan.md)，采用：

**在对象所属队列分片提取值 → 后台准备持久化输入并计算拓扑 → 主线程校验版本、分片判断和发布。**

目标是消除一次节点判断内同步构建整个空间拓扑的行为，覆盖基础拓扑、组成员索引、待加入/恢复组覆盖计划，以及首次 Site Zone 目标准备。

本计划为 R3 中关闭 P1 所需的实施单元。首版继续采用批次内复用；跨批次暖缓存、长期缓存淘汰和其他页面性能优化后续单独实施。现有命令生成、导入、清理回读及授权规则保持其独立入口；共享纯拓扑策略通过结果对照保证兼容。

已知基线：当前 macOS 隔离复测中，500 节点、50 组、每节点 20 个 Model，仅检查首节点，恢复字符串订阅查询后，完整主线程片段及后续回调等待约 222 ms。此数字用于确认阻塞存在，正式前后对比需要同设备、同数据、同构建条件重测。

## 2. 需要移除的同步重计算

| 当前入口 | 修复后的职责 |
| --- | --- |
| `NodeSyncStatusRefresh.step()` 中的首次节点检查 | 只有所需输入准备完成后才调用现有同步判断；等待期间保留请求。 |
| `NodeSyncReadContext.group(for:)`、`members(of:)` | 读取已准备的组归属和成员索引，禁止首次访问时扫描全网。 |
| `NodeSyncReadContext.plan(for:contextGroup:)` | 返回已准备的基础/覆盖结果，禁止 getter 内加载 Space 或调用全空间 planner。 |
| `NodeSyncReadContext.mergedTarget(for:local:)` | 读取已准备的 Site 结果，保持 localOnly、unavailable、site 三种状态。 |
| `GroupProximityLightingData.swift` 的对象适配层 | 增加值输入适配，与现有纯 `ProximityLightingTopologyPolicy` 共用计算规则。 |
| `SiteTriggerZoneTopologyReader.localTargetSnapshot(for:)` 的状态刷新路径 | 将持久化读取、输入验证、纯计算拆开，使用当前空间投影及其他空间的隔离持久化输入。 |

两个容易遗漏的分支必须同步覆盖：

- `getNeedSync()` 使用 `syncReadGroup ?? restoreData?.addGroup` 再次调用显式组判断，缺少成员时会构建 `additionalGroupMembers` 计划。
- 现有 `getNodeSyncProximityLighting(topologyPlan:)` 在显式传入计划时跳过 Site 合并。刷新器应注入完整的读取上下文，不能仅传入基础计划来替代当前链路。

## 3. 数据边界

建议增加 `NodeSyncTopologySnapshot.swift`、`NodeSyncTopologyPreparation.swift`；最终命名随项目惯例调整。

### 3.1 值输入与输出

| 数据 | 必需内容与约束 |
| --- | --- |
| 批次身份 | account、region、meshUUID、networkID、当前网络实例标识、批次 ticket；Site/Space 身份按依赖补充。 |
| 节点投影 | UUID、主地址、Vendor Model 归一化地址、空间标识、provisioner/configComplete/exitFailure 状态；Element/Model 顺序、有关订阅与恢复组标识。 |
| 组投影 | 地址、虚拟组标识、网络/空间归属、Profile 类型及 relay 参数、路径/区域成员、加载失败标志；保留网络内原组顺序。 |
| 空间投影 | 持久化 Space 的 triggerZones、加载完整性及版本；不得用调用者旧对象的秒级时间戳代替持久化内容。 |
| Site 输入 | Site 状态、当前与历史成员、各依赖空间的只读输入、权限/密钥一致性证据及依赖版本；复用当前策略所需的信息。 |
| 准备结果 | 节点归属、组成员索引、基础计划、已请求覆盖计划所需的节点目标和完整性、Site 目标、版本与失败原因。 |

后台纯计算输入只包含值。活动 `MeshNetwork`、`Node`、`Element`、`Model`、`Group` 和 UI owner 引用留在其所属队列。成员结果使用批次内稳定 ID，回主线程后分片绑定对象；保留现有 Node 身份/相等语义，不仅以地址判断对象归属。

### 3.2 分片提取

1. 明确 SDK 对有关字段的写入队列。当前代码要求刷新运行在主线程，但这本身不证明全部 SDK 写入均在主线程；实际写入需要经过同一所有权或同步边界。版本检查只能拒绝过期结果，不能代替数据竞争防护。
2. 保存节点、Element、Model、组路径/区域成员游标，每片从上次位置继续。节点筛选、组信息投影、最终对象绑定也计入预算。
3. 首选 App 侧使用 SDK 公开订阅接口逐 Model 提取，并立即转成值；同一个 Model 在一次有效提取中只读取一次订阅列表。保留 SDK 的字符串地址、虚拟地址、特殊组和主 Element 隐式 All Nodes 语义。
4. `Node.group` 按 SDK 的 Element/Model/组顺序及排除条件从投影派生，避免再次遍历 live 对象。不得直接用订阅集合的任意首项替代。
5. 测量最重单个 getter。若 `model.subscriptions` 自身在支持规模内超过预算，继续拆到 Model/Group 查询单元，并补齐特殊地址语义；若公开接口仍无法满足预算，才在现有本地 SDK 路径增加最小只读值投影接口，并验证所有引用 target。
6. 路径和区域中的成员逐段复制；禁止用整个 Mesh 的导出、JSON 编解码或含引用对象的浅拷贝充当快照。

分片软预算初值 **4 ms**，为调度、检查和发布留出余量；最终以完整主线程片段测量结果确定。至少在每个 Model 和长路径/区域的成员处理单元后检查预算，不能仅在一个完整节点处理完后检查。

### 3.3 持久化与 Site 读取

- 捕获明确的账户、区域、数据库路径和空间标识，由受控的只读存储边界读取 Space/Site/其他空间配置；后台入口不得重新根据可变全局账户寻找路径。
- 对需要 SDK 解码的持久化 Mesh，使用由该任务独占的对象图，且解码与读取接口已经核对线程安全；不从 `ProximityLightingTopologyContext.network(for:)` 回取活动 Mesh。
- Site 当前空间使用本轮 live 投影；其他空间使用隔离读取结果。旧 `resolvedMembers` 中依赖节点的地址转换也改用同一输入来源，避免某个辅助函数偷偷访问活动网络。
- 保留 Site 已确认版本、schema、当前/历史成员、权限、主网/子网密钥一致性及刷新阶段的验证。任何空间失败仍是 unavailable，不能变成空空间或 localOnly。
- 复用已实现的保护文件批次快照；所有依赖空间的状态均参与有效性检查。后台准备不会切换活动网络、安装密钥或发送命令。

## 4. 计算与刷新调度

### 4.1 后台计算

- 使用单个串行准备任务计算节点归属、组成员索引、基础空间计划和 Site 目标。优先直接调用现有纯 `ProximityLightingTopologyPolicy` 与 `SiteTriggerZoneTopologyPolicy`。
- 基础计划每个有效批次最多构建一次；组成员索引由订阅投影建立，避免每组重新扫描所有 SDK Model。
- 初始只准备当前请求需要的覆盖结果。刷新器预检每个节点可能用到的 nil group、实际组及 `restoreData.addGroup`；缺少覆盖计划时先提交后台计算，再进入 Bool 同步判断。
- 覆盖键包含批次版本、节点身份、显式组身份及相关投影。不同恢复组与 nil group 不合并；同一覆盖键只计算一次。第一版复用原纯策略生成覆盖结果，提取所需节点目标后释放临时整计划，控制内存。
- 真正未知的覆盖上下文必须触发重新准备或明确不可用，不能回落到主线程 planner。DEBUG 检查此契约；测试保证缺失输入不会形成“已同步”缓存。
- 组、空间及较长策略循环设置协作取消点。worker 接收取消 ticket；失效任务停止或完成后丢弃，避免多个整网计算同时运行。

### 4.2 生命周期

将分散的 `scheduled` / `preparing` 状态收敛为显式阶段：空闲、提取、准备、可计算/发布、失效待重读。每个异步完成回调同时校验 batch ticket 和请求版本。

- 同一活动 scope 合并 Cell、设备页和 warmUp 请求，只允许一个准备任务。计算中的请求更新只保留对应 owner 最新版本。
- 每个请求保存进度；可见请求优先，warmUp 按轮转推进。完成目标节点判断后及时回调，不等待全部预热结束。
- 取消 owner 仅取消其请求；最后一个 owner 取消时释放该任务。空间切换和版本失效取消旧批次。
- 旧任务回调只处理属于该任务且仍有效的请求，不能清空新请求。
- 对“版本过期，当前已稳定”重新准备；对“仍有 writer”等待变更结束或有上限的退避重试；真实不可读按当前保守不可用语义处理。重试不得以失效快照为依据结束后来提交的有效请求，也不得紧密空转。

上述最后两项同时覆盖 [1a55fe7 审查](260915_1803_review_1a55fe7.md) 中旧保护快照结束新请求的时序问题，属于异步刷新生命周期的直接依赖。

规划期间观察到工作区已有另一组进行中的修改：刷新器增加稳定新版本重读分支，测试补充 `protectionPreparationRaces()`。实施时以届时基线为准，复用这些改动及测试，重点验证它们在新增提取/拓扑阶段仍成立；本轮未修改或重新验证这组工作。

### 4.3 主线程读取和发布

`NodeSyncReadContext` 在进入节点判断前拿到准备结果，其成员、计划和 Site 目标读取均为内存查询。现有 Profile、场景、日程等判断先保留原规则，按节点分片执行，并继续测量单节点最大片段。

结果绑定、节点缓存写入、请求完成回调、context 释放都纳入完整片段计时。大结果转换分片进行；可在 worker 释放的纯值中间结果不集中交给主线程销毁。

## 5. 一致性与版本策略

批次绑定现有 `NodeSyncStatusGeneration`、`SpaceProtectionReadGeneration`、App/Mesh revision，以及实际 Site 依赖。进入/离开提取、持久化读取、后台计算及发布时检查相应版本。

- 对分片期间改变的订阅、组 Profile/路径、恢复组、节点状态及空间/Site 配置逐项审计失效入口。当前仅在两个节点缓存置 nil 时更新设备代数，不先假定已经覆盖所有相关修改。
- 不同快照读取阶段的版本必须一致；出现 writer、版本未知、账户切换或网络实例替换，整个准备结果不得发布为已同步。
- 发布使用现有保护版本的短临界区；其中只提交内存结果，不调用 UI、不执行 I/O。其他相关 live 写入与发布按已确认的所有权边界排序。
- 首版保留两库 revision 的一致性语义；提取片内优先做内存代数检查，实际两库核对位于受控读边界及发布验证阶段。
- `ConfigurationSnapshotRevision.current()` 当前依赖数据库连接、`totalChanges` 和 `PRAGMA data_version`。新只读连接不能直接生成同等语义的 token；`data_version` 也不能在不同连接之间直接比较。实现时需固定连接/协调边界并覆盖本进程写入，禁止仅把现有调用放到任意 worker。
- 发布验证若仍通过主线程访问现有数据库连接，必须单独计时并验证锁竞争。若无法满足完整片段预算，先完善存储 owner 的异步验证和进程内变更代数，再发布；不能删除核对来换性能。该项是验收门槛，不预先承诺现有 SQL 成本可忽略。

## 7. 验证设计

### 7.1 正确性

| 场景 | 检查 |
| --- | --- |
| 普通/虚拟/特殊组、主 Element All Nodes、多 Element、多 Model | 订阅、组归属顺序、成员索引与实际 SDK 一致。 |
| exitFailure、待加入/恢复组、显式 group 与 nil group | 覆盖计划与原规则一致，缺失覆盖输入不错误缓存已同步。 |
| 组路径、组区域、Space Zone、邻居容量边界 | targets、完整性及容量结果与旧纯策略一致。 |
| Site Zone 当前/历史成员、跨空间、旧地址格式 | 目标和异常语义一致；任一依赖不可读/不可用不变为空集合。 |
| 500 节点、14 个重叠 owner | 一轮基础计划；每个有效节点状态最多计算一次；覆盖按键去重。 |
| 取消、Cell 复用、同 owner 替换、账号/区域/空间切换 | 无过期回调、无新请求被旧任务清空。 |
| 提取/读取/计算/发布期间修改配置或保护状态 | 旧结果丢弃；写入完成后的新请求可自动获得新状态。 |
| 数据库版本未知、文件损坏、连续 writer | 保守失败/等待且不空转；不发布旧版本为已同步。 |

复用 `check_node_sync_status_refresh.py`、`check_space_protection_snapshot.py`、`check_sync_task_builders.py` 和拓扑策略回归。为新的异步读取/投影添加定向测试；独立脚本同步补全抽取源文件依赖。涉及共享策略变更时运行相应导入/清理回归。

### 7.2 性能与真机

- 固定 **500 节点 / 50 组 / 每节点 20 Model**。首先只请求首节点，再测全节点与 14 owner 重叠；另测跨空间 Site Zone、多个恢复组以及持续刷新/取消。
- 将真实 SDK 的 `Model.subscriptions` / `isSubscribed` 接入提取→拓扑→刷新链。允许其他边界保持隔离，但必须明确边界；独立调用 10,000 个 SDK Model 后再运行整数替身刷新不构成该验收。
- 使用 `AppPerformance` 增加提取、索引、后台基础/覆盖/Site 计划、发布验证和失效重读区间，保留完整 `SyncMainStep` / `SyncMainPrepare`。默认生产宏关闭；新增打印遵守 `#if DEBUG`。
- 同设备、OS、SDK revision、数据和 Release 优化条件建立提交前后对比。记录 App UUID；启用测量与关闭测量分别记录用途，不用不同构建间的时间宣称收益。
- MtestiPhone15 至少 5 次进程重启后的首轮、10 次同进程刷新。原 iPad 数据流程由人工复测；不使用 Simulator 或 Computer Use。

**P1 关闭条件：**

1. 状态刷新路径的全空间成员/拓扑/Site 计划构建在主线程执行次数为 0；只保留有预算的输入提取和结果处理。
2. 参考压力数据中，完整主线程片段 **P95 ≤ 8 ms，最大 ≤ 16.7 ms**。首次准备、DB 发布验证、覆盖计划请求与销毁均计入；超限必须定位处理后复测。
3. 首个节点计算前排入的主队列探针能及时运行；其等待与其他 UI/系统调度单独记录，不能只用后台总耗时或平均帧率代替最大片段。
4. 原约 222 ms 的隔离首节点长片段消失，真实 SDK 接入后的真机压力链也通过阈值；基准不能仅打印 PASS，超限应失败并保留样本。
5. 总刷新时间、CPU 秒、计算次数和峰值内存同时记录，确认没有通过重复/无界后台工作转移问题；原单批次基础计划去重保持成立。
6. 真机检查首次进入 Groups/Devices、滚动复用、同步标记、清理/导入完成后刷新及连续切换空间的响应。最终体验由人工确认。

构建使用直接 `xcodebuild`、`iphoneos`、`generic/platform=iOS`、关闭签名方式，覆盖受影响品牌；共享同步状态代码实际运行以 MtestiPhone15 的主 App/专用测试工程为主。没有真机结果时，交付状态只能是代码与隔离回归完成、性能验收待完成。
