# 网关本地优先删除与异步云删除方案评估

- 日期：2026-09-16。
- 背景：用户已确认以 Site Owner 复现。此前的根因分析见 `260916_1045_gateway_delete_scope_analysis_plan.md`。
- 本轮需求：评估“先 Reset，成功或强制删除后更新本地并生成云同步任务”，补充必要边界；再次核对是否与未绑定 Spaces 有关。
- 状态：历史方案评估，已被用户更新的 `260916_1131_gateway_online_server_first_delete_decision.md` 替代，不再作为当前实现依据；尚未修改业务代码。下文保留本地优先方案的分析背景。

## 1. 结论

用户方案可行，更符合“正常 Reset 失败后，取消强制删除，不再由 App 删除本地和云端数据”的交互预期。

相比当前服务器优先流程，它将需要处理的中间状态改为“本地已删除，等待云端删除”。只要删除意图能持久化、云端旧数据不能把设备重新导入、同一网关的新注册不会被旧删除任务误删，产品流程可以保持简单。

无需另建一套通用云同步框架。建议复用现有请求层、网络恢复通知和 Site 同步反馈，增加一个明确的网关删除任务和少量持久化状态。

## 2. 推荐的用户流程

1. 点击 Delete → Continue，完成必要的权限和本地上下文预检。
2. 发送蓝牙 Mesh `ConfigNodeReset`，等待结果。
3. 收到成功回执：完成本地业务清理，并可靠记录待云端删除任务。
4. 无法确认成功：显示强制删除确认。
   - FORCE DELETE：完成同样的本地清理和待云端删除记录，保留需手动重置的现有说明。
   - Cancel：不主动继续删除、不提交本次云删除任务，保留设备记录供重试。
5. 后台执行 `gatewayDelete`，成功后结束待同步状态；网络暂时失败则保留并重试。

本地设备列表可以在第 3／4 步完成后移除网关，无需等待云请求。Site 同步状态应能表达仍有待提交删除，不能把本地移除直接显示成所有端均同步完成。

## 3. 必需补充之一：这是“云删除任务”，不是现有 syncGateway

已核对当前代码：

- `SyncOperation` 只有 `syncSite`、`syncSpace`、`addSpaces`、`syncGateway`，没有网关删除操作。
- `syncGateway` 的 API 构造执行 `gatewayRegister`；实际同步执行路径也进入 `GatewayServerAuthorizationService.authorizeWithReceipt`，语义是注册／更新。
- `SiteData.export` 并不通过一个权威 Gateways 列表表达删除；仅同步 Site 不能替代明确的 `gatewayDelete`。
- `CloudSynchronizationManager.syncHandles` 是内存数组，任务失败会移出数组；现有前台／恢复网络补偿主要重建 Site／Space 的待同步工作，没有已删除网关的恢复任务。

因此要增加明确的云删除任务，使用现有 `gatewayDelete` 接口，不能把已删除网关再交给 `syncGateway`。

待删除记录至少包含账号、服务器区域、Site ID、网关 MAC，以及区分旧 Node 实例的 UUID／地址和操作 ID。重试只需要删除标识，不应为了任务而保留或新增 Mesh／MQTT 密钥等授权信息。任务应按其原始账号与区域执行，不能在切换账号或服务器后误发。

本地业务删除与“需要云删除”的持久化记录应在可控的本地事务中一起提交。SDK 的 Mesh 数据库与 App 数据库是不同边界，不能假设所有操作可用一个事务跨库完成；需要第 6 节的操作记录补齐中断恢复。

## 4. 必需补充之二：待云删除时，旧数据不能恢复设备

当前 `ImportData.swift` 会把云端 `gateways` 中本地没有的网关重新导入。本地优先删除后，在云请求成功前，服务器仍然正常返回这个旧网关。

因此：

- 导入前识别本机待云删除的旧网关，避免重建其 Node、GatewayModel 和旧关联。
- 暂停／取消目标网关已有的注册或更新任务；等待在途授权请求妥善结束，防止删除后又注册。
- Reset 失败且取消时恢复原有正常同步资格，不留下一个永久阻止正常使用的删除状态。
- 删除确认后也要处理此前发出的迟到 Site 响应，例如使旧导入请求失效或按请求代次拒绝旧结果。不能删除任务记录后立刻接受一份删除前的旧快照。

这条保护方向与原服务器优先方案不同：原方案要保留“尚待 Reset”的本地设备；新方案要防止“本地已经删除”的设备被云端旧数据重新创建。

## 5. 必需补充之三：删除后重新添加同一网关的顺序

当前 `gatewayDelete` 请求只传 `gatewayId`（MAC）和当前 `userId`，不携带旧 Node UUID 或注册代次。若旧删除任务仍在重试，又先完成同一 MAC 的新注册，旧任务可能删除新记录。

建议最小规则：**同一网关的旧云删除确认完成后，才提交其新的云注册。** 本地扫描到未配网广播与允许新的云注册是两个不同边界。若产品允许先本地重新配网，新注册仍需排在旧删除后执行，并保留其待同步状态。

同一 App 内按网关串行化删除／注册即可覆盖普通重新添加场景。若还要求离线旧删除任务与另一台手机的新注册同时发生时也绝不误删，则需要服务端按旧实例／版本做条件删除；只凭 MAC 的客户端重试不能保证这一点。

既有历史决定已记录 `gatewayDelete` 对已不存在的网关按幂等成功处理，异步重试可继续使用该合同。权限拒绝等不能靠等待恢复的失败应保留错误供处理，不无限快速重试，也不能让本地已删除网关悄悄恢复。

## 6. 必需补充之四：Reset 回执与中断边界

### 6.1 SDK 已自动移除本地 Node

锁定 SDK `a6246b1b0409824a3227a9c7cad8140219feb182` 的 `ConfigurationClientHandler` 在收到 `ConfigNodeResetStatus` 时立即调用 `meshNetwork.remove(node:)`，早于 App 的完成回调。

这与“Reset 成功就本地删除”的新方案一致，不需要之前讨论过的“延迟 SDK 删除直到云端成功”机制。

但如果 App 在 Node 已移除、待云任务尚未写入之间退出，仍会丢失云删除意图。因此建议：

- 发 Reset 前，落盘一条内部准备记录，保存最小身份信息；不改变可见设备／关联，不执行云删除。
- 成功回执或用户强制删除后，将记录推进为需要云删除，并完成本地业务清理。
- 取消且没有成功证据时，撤销准备记录，不生成云删除任务。
- 重启后依据阶段及捕获范围恢复清理；本地 Node 缺失不是硬件已 Reset 的绝对证明，恢复界面和日志需区分“物理成功已确认”与“完成本地清理”。

App 侧不能再使用“必须找到 Space”的通用删除上下文。Site 主网络网关须以 Site／主网络为范围执行上述流程；普通 Space 设备保留原保护。

### 6.2 Cancel 无法撤回已经执行的 Reset

“失败”需要区分：

- 命令确定未发送：取消后可以保持本次删除前的数据及硬件状态。
- 命令发出但未收到回执：设备可能已经 Reset，只是回执丢失。App 无法从超时证明硬件没有变化，也无法通过取消使设备重新入网。

因此可保证的产品语义是：**没有确认成功且用户取消时，App 不主动继续删除，不提交云删除。不能承诺硬件绝对没有变化。**

迟到成功回执仍可能被 SDK 处理并移除 Node。实现应以一次操作的唯一结果进行收敛：成功已经确认时不再作为普通失败取消处理；超时弹窗仍显示时收到成功应关闭／更新弹窗，避免同时报告失败与成功。严格要求“按 Cancel 后连迟到 Reset Status 都不得改本地”会超出现有 SDK 行为，需要另外定义和实现回执处理规则，而且仍无法撤销硬件 Reset。

## 7. 权限、关联与反馈保持简洁

- 本次 Owner 场景可按本地优先流程进行；网络离线时可在本地操作后保留待云删除。
- 非 Owner 仍应在 Reset 前完成既有 Associated Spaces 权限预检。离线且无法完成预检时，建议沿用拒绝开始删除的规则，不默默放宽编辑者权限。
- 云端删除最终失败时不能回滚已经 Reset 的硬件。保留云任务与错误，通过 Site 同步反馈提供重试／处理入口。
- 本地提交删除后清理相关 Space 的网关关联显示，云端由 `gatewayDelete` 清空关联；无须额外逐个发送解绑请求。待同步期间旧 Site 快照不能把关联显示重新恢复，也不能误伤后来绑定的新网关。
- 强制删除仍意味着没有确认物理退网，继续保留“需要手动重置”的提示。
- 若新增状态提示，补齐英文和简体中文，使用既有同步提示组件。

## 8. 与是否绑定 Spaces 的关系

**未绑定 Spaces 不是本次问题的触发条件；绑定后仍可能稳定命中同一错误。**

必须区分：

| 概念 | 作用 | 对本次删除准备检查的影响 |
| --- | --- | --- |
| 网关所属网络 | 从 Site 添加时是 Site 主网络，Node 的 `subNetworkId` 记录这一归属 | 当前错误代码试图用它查找一个 Space，查不到 |
| Associated Spaces | 网关跨子网控制的关联；同步相应 Secondary Network Keys、App Keys、模型绑定及索引 | 不会把网关所属网络改成这些 Space 中的某一个 |

代码依据：

- `SiteDeviceAddViewController.swift:446`：添加前确保当前为 Site 主网络。
- `DevicePermanentDeletionCleanup.swift:19–35`：依据 Node 的 `subNetworkId` 查 Space，并要求当前网络匹配；没有读取 `gateway.associatedSpaces`。
- `Node+SyncData.swift:1727–1794`：绑定／解绑 Associated Spaces 围绕额外的子网 Key、App Key 和索引生成任务。
- SDK `MeshLib/Node/Node+Propertys.swift:708`：`subNetworkId` 使用缓存／数据库恢复的归属 ID；没有根据 `associatedSpaces` 自动改写归属的规则。其旧的“取第一个 Secondary Key”实现是注释，不是当前执行代码。

未绑定、绑定一个、绑定多个 Spaces 都应进入修复验证。关联数量仅影响权限检查和删除后的关联清理，不决定是否需要真正发送 Reset。

## 9. 最小落地与验证范围

推荐分三块完成：

1. Gateway 共用删除流程改为先 Reset，明确成功／强制删除／取消三个结果；修正 Site 与 Space 的范围混用。
2. 增加持久化云删除任务，接入已有请求、恢复网络／回前台重试及 Site 同步反馈。
3. 导入和注册读取删除状态，防止恢复旧网关及旧任务删除新注册。

优先覆盖行为测试：无 Space 的 Site 网关；关联 0／1／多个 Space；WiFi／4G；Reset 成功；失败取消；失败强删；回执丢失／迟到；网络离线／重启；云删除失败后重试；删除期间 Site 刷新；同一 MAC 重新添加；Owner／Editor 权限。

普通网关删除无需增加复杂的新页面或修改整个 Space 删除体系。涉及共享代码、本地化或数据库变更时仍检查全部品牌 target，并按工程要求直接构建 generic iOS、使用允许的真机验证硬件退网和重新添加。
