# AGENTS.md 分析范围优化建议

日期：2026-09-29。范围：全局与当前项目规则，结合 2026-09-23 至 2026-09-29 的近期会话抽查。仅新增本分析文档，未修改两份 AGENTS.md、业务代码、测试或其他工作树。

## 结论

建议同时优化全局和项目规则，明确三个范围：**分析覆盖完整关联行为，实施选择最小完整改动，验证覆盖已识别风险。**

当前限制无关重构、擅自扩大需求和机械全量验证的规则应保留。主要缺口是没有明确规定：在决定“小范围修复”之前，需要检查哪些上下游、同类入口、数据与生命周期状态；需求分析还应提前比较复用现有机制的方案。

这不是要求每次全仓审计或固定执行“8 横 8 纵”。小文案、小样式仍可简短分析；共享能力、持久化、同步、协议和异步状态变化则需要覆盖有实际关联的完整路径。扩大只读分析本身不需要再次征求实现授权。

## 两份规则的关系与缺口

已核对 [全局 AGENTS.md](/Users/maginawin/.codex/AGENTS.md) 和 [项目 AGENTS.md](../AGENTS.md)。两处均没有同级 `AGENTS.override.md`。当前文件分别为 4,443 与 7,360 字节，合计约 11.5 KiB；仅就这两份文件而言，没有达到默认 32 KiB 限额。

OpenAI Docs 说明全局与项目说明会叠加，更接近当前目录的规则覆盖冲突内容。因此建议全局放通用分析原则，项目补业务路径，避免只在项目新增一句“扩大分析”而保留原有模糊措辞。[官方规则说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

| 现有规则 | 已有价值 | 需要补充的边界 |
| --- | --- | --- |
| 全局“先找与症状直接相关的证据，修复最小完整行为链” | 从证据入手、避免泛化重构 | 明确症状是调查起点；找到直接原因后仍需核对成因、同类消费者和后续恢复 |
| 全局“保持改动聚焦”“不要反复全仓扫描” | 控制修改与搜索成本 | 不限制沿调用、数据和状态依赖进行定向扩展 |
| 全局“范围清楚、可逆的小修改直接推进” | 避免流程过重 | 不能仅凭用户描述短、拟改文件少就认定影响小 |
| 全局“检查通过后结束验证” | 防止无意义重复验证 | 检查集合应先与影响分析匹配，不能只因已有脚本通过就认为遗漏路径已覆盖 |
| 项目“修复前确认……最小影响链” | 约束实现 | 分析阶段不应预先以“最小”截断影响链；应先识别关联范围，再收敛改动 |
| 项目已有导入/同步回归、跨品牌与 SDK 规则 | 已覆盖部分横向影响 | 多数写在改动或验证阶段，缺少需求与方案阶段的明确执行要求 |

这些文字存在偏向收窄的解释空间，但会话无法证明某次缺陷由某句规则直接造成。以下区分实际遗漏、后续需求调整和做得较完整的分析。

## 建议写入全局 AGENTS.md 的原文

建议在“执行方式”后新增“分析与规划范围”，用以下六条统一跨项目原则：

> - 分析范围与修改范围分别确定。分析问题、分析需求、规划开发时，先覆盖与目标相关的完整行为链及受影响范围，再收敛最小完整改动；不以用户提到的页面、单个报错点或预计修改的文件作为分析边界。
> - 问题分析从直接证据向上游来源、下游消费者和同类入口扩展；需求分析核对用户目标、现有行为、适用对象、关键边界及验收标准。沿调用、数据和状态依赖定向展开，小修改可简短完成，不固定做全仓扫描或穷举矩阵。
> - 规划前检查现有共享组件和机制的全部相关使用方，优先比较直接复用、必要扩展与独立实现的差异。提前说明复用带来的行为联动；会改变需求、兼容性或实施方向的未决项再提问，不因局部隔离而默认增加新抽象。
> - 涉及状态、持久化或异步操作时，按风险检查正常、合法空值/旧数据、失败/重试/取消、退出重进或重启恢复路径。新增拦截需说明应拒绝与应允许的场景，并检查本次状态变化是否会阻断自己的后续流程。
> - 方案说明已证实事实、关键假设、关联影响、必要改动及验证方式；区分本次必须解决的关联问题与可后续处理的问题。不能因为保持小改动而省略必要一致性保障，也不把发现的其他问题自动纳入实施。
> - 当已能解释问题或需求的端到端行为、识别相关使用方与关键状态风险，并据此给出实施和验证边界时结束扩展分析；缺失证据明确列出，不用无关调查、额外流程或反复确认代替结论。

同时调整两处旧措辞，避免新增规则与旧规则相互拉扯：

1. 将“先找与症状直接相关的证据，修复最小完整行为链；区分已证实原因和假设。证据不足时补最小诊断，不靠扩大架构解决未知问题。”替换为：

   > 从与症状直接相关的证据入手，按“分析与规划范围”核对成因及关联影响，再实施最小完整修复。区分已证实原因和假设；证据不足时补必要诊断，不靠扩大架构解决未知问题。

2. 将“检查通过后结束验证”所在条目替换为：

   > 与影响分析匹配的必要检查通过后结束验证；已有脚本未覆盖的关键路径应明确补充验证或列为待验收，不能视作已通过。只有新修改、新失败或明确未覆盖风险才扩大或重跑；复用结果时确认代码差异、配置及依赖仍一致。

其余轻量执行、权限、保护未提交改动、真机验收及避免无关重构的要求保留。

## 建议写入项目 AGENTS.md 的原文

建议在“改动边界与业务验证”前新增“分析范围与业务链路”，仅保留本项目特有要求：

> - 根据任务沿实际链路分析：页面入口与权限 → Site/Space/Group/设备模型及归属 → 本地存储与导入导出 → 同步任务及 App/SDK/网关交互 → 回执、状态刷新与再次进入。覆盖共享同一数据或能力的相关入口，按依赖选择环节，不将同名 Site/Space 功能等同，也不要求每次检查全部模块。
> - 同步、删除、恢复与完整性校验方案同时检查：异常如何产生、当前在哪里阻断、其他入口是否也受影响、存量状态怎样恢复。核对合法空配置与旧格式、正常上传/导入、失败重试及持久状态的连续转换；避免新保护阻断合法配置，或本次操作创建的记录使自己失效。
> - 设备能力与 Group 行为需求先核对共享能力表、UI、任务生成、配置下发和恢复路径的联动。涉及 SDK、固件或云端契约时沿实际依赖继续核对；区分已证实能力与 App 当前表现，缺少外部证据时说明假设，不擅自推定支持范围。
> - 规划中明确本次必要的 App/SDK/配置或服务端配套、历史数据处理、受影响品牌与验证边界。相关实现或运行证据不可获得时标明限制，不能以本地单个入口或隔离测试结果推定完整业务链已经成立。

将原“修复前确认触发条件、预期行为和最小影响链”所在条目替换为：

> 实施前基于上述分析确认触发条件、预期行为和关联影响，选择满足当前需求及必要一致性保障的最小完整改动。优先复用已有同步、取消、重试和持久化机制，不以改动文件少替代行为完整。

项目原有的回归枚举与多品牌/SDK 构建规则继续保留，不再复制进新增段落。

## 如何判断优化是否有效

后续代表性任务应能在首份方案中回答：

1. 网关时区任务：除了筛选目标，是否解释残留记录来源、其他消费者以及清理与保留的取舍？
2. 新设备能力：是否提前列清现有能力名单的联动，先比较复用方案，再决定是否拆独立逻辑？
3. 缓存/异步优化：是否覆盖状态失效后的重建，以及离开、取消、回来时的行为？
4. 同步保护/删除：是否检查合法输入与正常流程、历史阻断恢复、外部动作成功后的本地收尾？

这些是分析质量的观察项，不是每次任务都要新增的测试。小改动仍直接推进，非目标问题只记录；扩大只读分析不等于扩大代码授权、自动运行真机或启动多轮子代理。
