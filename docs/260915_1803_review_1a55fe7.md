## P2：旧保护快照会错误结束写入完成后的新刷新请求

位置：`SunSmart/Common/Data/NodeSyncStatusRefresh.swift` 第 104–107 行。

后台读取与主队列发布之间存在时间窗口。若期间导入或清理完成，使保护代数变化，并由页面重新提交刷新请求，新请求仍等待同一个 `preparing`。旧快照回调进入 `finishUnavailable()` 后，会清空当前的全部请求并返回 `true`，包括在写入完成后提交的新请求，而不是重新读取已经稳定的保护状态。

这会让成功导入/清理后的刷新显示错误的“需要同步”状态。`GroupsViewCell` 收到 `true` 会显示 `sync_failed_big`，设备页面会显示同步按钮；调度器不会自行再次刷新。空间进入流程中的 `reconcileLegacyProximityLightingTopology()` 在清理成功后调用 `reloadData()`，是实际存在的写入后刷新入口。

隔离复现使用仓库生产调度器、保护读取器、上下文及拓扑代码，在 `ProtectionRead` 返回前暂停 worker，让保护写入开始并完成，再替换同一 owner 的请求。结果：

- 新鲜保护快照：`isBlocked = false`。
- 更新后的请求：`needsSync = true`，节点检查次数为 0。
- 再次手动刷新：`needsSync = false`。
- 临时复现源：`/tmp/review_1a55fe7_status_race.swift`。

应区分“当前仍在写入/文件不可读”和“旧版本已经失效但现在可以稳定读取”，至少保留写入结束后的新请求进行重读，而不是用旧批次的不可用结果结束它们。本次只验证了生产控制流的隔离复现，不视为真机 UI 验收。
