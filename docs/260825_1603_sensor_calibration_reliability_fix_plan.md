# Calibration 页面三种校准模式可靠性修复规划

## 1. 结论

本轮建议进入修复规划，但先聚焦“不断电条件下，一轮校准是否可信且能够明确成功/失败”，暂不扩展到断电持久化读回和 Auto 闭环最终收敛。

建议本批次处理以下 4 个行为问题：

1. 将 Sensor、Plane、Night 三种模式的亮度点采样统一为“最小等待 + 主动轮询 + 稳定窗口 + 趋势停止 + 总超时”，而不是固定等待后单次读取。
2. 把目标 Lux 传入 Sensor 校准流程，在写入 `0x38`/`0x39` 前完成可达性校验。
3. 保留 Group Unack 作为高效下发手段，但增加逐灯状态核验和定向补偿，未确认完整 Group 到位时禁止采样。
4. 修复零样本稳定性误判，并严格校验 publish delta 恢复 ACK；恢复失败不得报告整轮成功。

这些问题会直接影响本轮校准数据是否可信，不能只作为日志增强处理。

已确认的产品语义：

- Sensor 目标 Lux 的允许下浮范围为 5%，即 100% 稳定值达到目标值的 95% 即可视为达到目标，不强制要求稳定值大于或等于目标原值。
- 暗环境能力不足按硬失败处理；暗环境能力同样使用目标值的 95% 作为最低可接受下限。
- Group 任一必要灯具离线或持续无法到达目标 Lightness 时，本轮校准硬失败，不允许按剩余灯具降级生成曲线。
- 稳定采样、Group 到位确认、零样本处理和 publish delta ACK 门控等共性问题必须同步修复 Sensor、Plane、Night 三种模式。

## 2. 稳定采样方案

### 2.1 对“3 秒后每秒读取，连续 3 次不再变化”的调整

方向正确，但不建议直接把全过程最大值或最小值作为最终校准值，原因包括：

- 传感器量化、Mesh 时延和环境扰动会造成 1～2 lx 抖动；严格要求数值不变容易误超时。
- 瞬时反光、人员走动或灯具过冲可能产生离群最大值/最小值。
- 仅检查“不再增加”或“不再减少”，可能在缓慢漂移时过早结束。
- 只修 0% 和 100% 仍会让 25%、50%、精细搜索点使用不稳定数据，最终拐点仍不可靠。

推荐统一建立一套稳定采样器，应用于 0%、粗搜点、精搜点和 100%：

1. 下发目标 Lightness，并确认完整 Group 已到位。
2. 至少等待约 3 秒，避免把明显过渡阶段计入稳定判断。
3. 此后每约 1 秒主动执行一次 `SensorGet`。
4. 按本次亮度相对上一点的变化方向维护方向极值：上升过程维护最大值，下降过程维护最小值。
5. 只有同时满足以下条件才判定稳定：
   - 最近稳定窗口的 Lux 极差在容差内；
   - 方向极值连续 3 次比较都没有超过容差的有效改善；
   - 已获得规定数量的有效响应。
6. 到达单点超时仍未稳定时，明确返回“灯光/传感器未稳定”，不得拿最后一次值继续校准。
7. 最终校准值取稳定窗口的中位数或去极值平均值；全过程最大值/最小值仅用于判断平台和诊断，不直接作为写入值。

“连续 3 次比较”至少需要 4 个有效样本。Lux 容差、窗口大小和单点超时应集中配置，并通过真机数据定值；不建议把“完全相等”作为条件。

### 2.2 100% 与 0% 的取值

- 100%：等待上升停止，取最后稳定窗口的代表值作为 `sensorOnLux`。
- 0%：等待下降停止，取最后稳定窗口的代表值作为 `sensorOffLux`。
- 可达性校验可使用更保守的窗口边界，例如 ON 窗口低值、OFF 窗口高值，避免在临界目标上误判可达。

本 Log 中 100% 首次读取为 86 lx，之后仍出现 89、94 lx，按上述规则不会在 86 lx 处结束。

### 2.3 Night 模式现有稳定判断也要统一

Night 当前已有多次采样，但本质上主要检查最近窗口的极差。类似 83、86、89 这种持续上升的数据，窗口极差仍可能落在现有阈值内，因此仍可能被提前视为稳定。

建议 Night 也复用同一稳定采样器，再保留 Night 特有的成对采样和最小 Lux 差要求，避免三套模式出现不同的“稳定”定义。

### 2.4 超时边界

所有亮度点都改成稳定采样后，当前整段流程的固定总超时可能不够。实现时需要同时调整：

- 每个亮度点有独立 deadline；
- 整轮有更大的总 deadline；
- 超时错误携带模式、Lightness、有效样本数、最后窗口及失败阶段；
- 用户停止仍应优先终止采样、清理状态并恢复控制权。

## 3. 目标 Lux 可达性校验

### 3.1 是否需要修复

需要。当前 `0...2500` 只验证输入格式/协议范围，不能证明目标在当前灯组能力范围内。`0x38` ACK 也只证明设备接受了曲线参数，不能证明目标 100 lx 可达。

建议把页面输入的目标 Lux 显式传入 SDK 的 Sensor 校准调用，在稳定 OFF/ON 数据获得后、写入新 `0x38`/`0x39` 前校验。失败时走统一回滚，不覆盖旧的有效校准状态。

### 3.2 建议分成三层

1. 计算目标下限：`minimumReachableLux = targetLux × 95%`。使用原始精度比较，不要先做会扩大容差的整数截断；用户输入 100 lx 时，最低可接受值为 95 lx。
2. 当前条件硬门槛：稳定后的 100% 总 Lux 低于目标下限时直接失败；达到或高于目标下限即可通过，不强制要求达到目标原值。本 Log 已观察到的最高值 94 lx 对目标 100 lx 仍应失败，但必须以最终稳定窗口为准，不能用过渡期单点判定。
3. 暗环境能力硬门槛：用 `stableOnLux - stableOffLux` 估算灯具自身可提供的 Lux。该贡献值低于目标下限时直接失败，因为没有外部光时灯组无法在允许的 5% 偏差内达到目标。
4. 调节余量：5% 是目标达成容差，不等同于控制器调节余量。本批次不再额外设置“100% 必须高于目标一定比例”的硬门槛，但应记录剩余余量，为后续闭环饱和问题分析提供证据。

建议新增明确失败原因，区分“Sensor 无响应”“环境不稳定”“当前条件不可达”和“暗环境能力不足”，不要统一显示普通校准失败。

该目标 Lux 可达性规则是 Sensor Cal. 的模式特有校验。Plane Cal. 的外部照度计输入、Night Cal. 的目标亮度和 Lux 差要求继续保持各自语义，但两者必须使用修复后的稳定样本和完整 Group 状态，不能机械套用 Sensor 的目标 Lux 公式。

## 4. `0x38` 曲线在三种模式中的作用

按当前 App/SDK 流程，Sensor、Plane、Night 都会走同一套灯具 Lightness—Sensor Lux 拐点搜索并写入 `0x38`，因此这条曲线在三种模式中都有用：

- Sensor Cal.：使用实际灯组对 Sensor 的 Lux 贡献曲线，`0x39` 使用 Sensor/环境倍率 100/100。
- Plane Cal.：同样需要 `0x38` 灯具贡献曲线，再通过外部照度计数据计算 `0x39`，把 Sensor 读数映射到工作面。
- Night Cal.：仍需要 `0x38` 曲线，并在暗环境流程中增加目标亮度相关的稳定成对采样；当前倍率同样按 100/100 下发。

这里能够确认的是 App/SDK 的参数生成和下发设计。固件内部最终如何组合 `0x38`、`0x39` 参与控制，仍需固件接口定义或固件侧日志证明，但这不影响本次必须保证曲线采样可信。

## 5. Group Unack 的修复策略

### 5.1 风险判断

该问题对三种模式都成立，因为三种模式共用 `0x38` 曲线采样。任何参与 Group 光输出的灯具未到达目标 Lightness，都会改变 Sensor 看到的总 Lux，使曲线不再代表完整 Group。

不建议直接改成 acknowledged group multicast。大型 Group 会产生响应风暴，且难以可靠关联每个成员。

### 5.2 推荐的混合方案

兼顾正确性和大型 Group 性能，建议采用：

1. 先按现有方式向 Group 发送 Unack Lightness，可使用受控的 Mesh retransmit，而不是在业务层无上限重复。
2. 根据 Group 配置枚举所有会贡献照明输出且支持 Light Lightness 的节点。
3. 最小过渡时间后，逐节点单播读取 Lightness；限制并发数，避免瞬时拥塞。
4. 对未响应、仍在 transition 或 Lightness 不匹配的节点，执行有限次数的单播 acknowledged 修正并再次核验。
5. 只有所有必需节点都响应并到达目标，才开始稳定 Lux 采样。
6. 有节点离线或多次不匹配时，本轮校准失败并恢复旧配置；不应静默排除该节点后继续生成“完整 Group”曲线。

如果首版更重视实现简单和最强确定性，也可以每个点都直接使用逐节点单播 acknowledged Set。它更慢、消息更多，但校准是低频操作，正确性优先。推荐最终仍采用上述“Group 快速下发 + 单播验证/补偿”，扩展性更好。

需要同时明确哪些节点属于“校准贡献节点”，避免把纯传感器、开关或不具备 Lightness 输出的节点纳入等待集合。

## 6. 环境稳定性零样本问题

### 6.1 是否可以不修

不建议。零样本表示没有观测证据，继续执行会把通信故障、Publication 配置失败或 Sensor 不在线误判为环境稳定。这会直接污染后续所有采样点。

### 6.2 修复建议

- 初始环境稳定性检查改为主动 `SensorGet`，不要只依赖被动 Publication。
- 必须达到最少有效样本数后才能判断稳定。
- 零有效样本或响应不足返回 Sensor 无响应。
- 样本足够但趋势/极差不满足条件，返回环境不稳定。
- 复用统一稳定采样器及其容差、趋势和超时规则，避免入口检查与亮度点采样标准不一致。

后续可再增加“开头 0% 与结尾 0% 基线复测”来识别整轮过程中环境光漂移。这是提升重复性的第二阶段措施，不阻塞第一批核心修复。

## 7. publish delta 恢复 ACK 校验

建议加入严格校验，不只是判断回调被触发：

- 响应必须来自目标节点；
- Response Code 必须是 `daylightPublishDelta`；
- status 必须为成功；
- 超时、错误码或错误响应执行有限次数重试；
- 重试仍失败时，不得触发 SDK 校准成功。

同时要把 publish delta 恢复纳入失败清理。否则前面任一步失败后，Sensor 可能长期停留在校准用的 delta=1。

推荐事务语义为：只有新曲线写入、倍率写入、publish delta 恢复以及必要清理全部成功，SDK 才向页面报告成功。恢复失败时尝试回滚旧校准并再次恢复 delta；如果仍无法恢复，应保持 Auto 暂停，明确提示用户执行重试/恢复，不能伪装成成功。

## 8. 本批次范围与暂缓项

### 本批次纳入

- 三种模式统一稳定采样。
- 所有曲线采样点的 Group 到位确认。
- Sensor 目标 Lux 可达性校验。
- 零样本稳定性修复。
- publish delta ACK 门控和失败清理。
- 支撑上述行为验收所必需的采样及决策日志。

### 本批次暂缓

- `0x38`/`0x39` GET、NVM 读回和断电重启验证。
- 恢复 Auto 后长期闭环是否最终收敛到目标 Lux。
- 面向生产排障的完整终态可观测性体系。

暂缓完整可观测性不代表本批次不加日志。没有逐点样本、稳定判定、节点到位和 cleanup ACK 日志，就无法验证行为修复是否有效。

## 9. 推荐实施顺序

1. 抽取统一的 Lux 稳定采样策略与结果模型，先用确定性样本序列建立单元测试。
2. 将 Plane/Sensor 单次读取和 Night 现有窗口判断迁移到统一采样器。
3. 增加 Group 节点发现、单播状态核验、补偿和失败结果。
4. 将目标 Lux 传入 Sensor 校准，加入当前可达性、暗环境能力和余量决策。
5. 修复初始环境稳定性零样本语义。
6. 严格门控 publish delta 恢复，并补齐失败清理。
7. 补齐本批次结构化诊断事件，再执行自动化、四 target 构建和真机矩阵。

以下产品语义已经确认，可直接作为实施和验收条件：

- 暗环境能力低于 Sensor 目标值的 95% 时硬失败。
- Group 中有一台必要灯具离线或持续不到位时硬失败，不允许降级校准。
- 三种模式的共性采样与 Group 可靠性问题同步修复。

## 10. 自动化验证

### 10.1 稳定采样测试序列

- 持续上升：83、86、89、94，验证不会在 86 或 89 提前结束。
- 上升后小幅抖动：验证稳定窗口能够收敛。
- 持续下降后平台：验证 OFF 取稳定窗口代表值。
- 瞬时过冲/反光：验证离群最大值不会直接写入曲线。
- 缓慢单向漂移但窗口极差较小：验证趋势条件能够阻止假稳定。
- 全程无响应、部分丢响应、超时：验证错误分类和停止行为。

### 10.2 业务状态测试

- Sensor 目标明显可达、恰好达到 95%、略低于 95%、当前不可达、暗环境能力不足。
- Group 全员到位、单节点首次丢包后补偿成功、节点持续离线、节点 Lightness 不匹配。
- publish delta 首次失败后重试成功、持续失败、错误 Response Code。
- 任意阶段失败时旧校准、Publication、publish delta 和 Auto 状态的恢复边界。

### 10.3 工程验证

实现后至少执行聚焦测试、相关 SDK 测试，并直接使用 `xcodebuild` 验证 SunSmart、Archipelago、SLG Sync Plus、SylSmart 四个 target 的真机 SDK 构建，不使用 Simulator 代替。

## 11. 完整真机测试与调试闭环

行为修复完成后，建议按一轮唯一 `calibrationRunId` 串起 App 与 SDK 日志，形成以下闭环：

1. 开始：模式、目标 Lux、Group、Sensor、参与灯具列表、原配置快照。
2. 控灯：每个 Lightness 点的 Group 下发、逐灯核验、补偿次数和最终结果。
3. 采样：每次 SensorGet 的时间、值、有效/过期判定、稳定窗口、方向极值和结束原因。
4. 决策：OFF/ON/拐点结果、目标可达性、余量判断及最终 `0x38`/`0x39` payload。
5. SDK 提交：`0x38`、`0x39`、publish delta 的发送、ACK、重试和回滚结果。
6. App 提交：Sensor Publication、逐灯 Profile、场景保存、云同步和 Group Auto 恢复结果。
7. 终态：整轮 `app_complete` 或明确的 `app_failed`，包含首个失败阶段及 cleanup 是否完整。

### 11.1 真机矩阵

- 模式：Sensor、Plane、Night。
- Group：单灯、当前三灯、多灯 Group。
- 目标：明显可达、临界、明确不可达。
- 环境：稳定、缓慢变化、突发遮挡/反光。
- 网络：正常、单节点丢包、节点离线、Proxy 路径变化。
- 流程：成功、用户 STOP、采样超时、提交失败、cleanup 失败。

Plane 必须使用外部照度计记录工作面值；Sensor 以目标 Sensor Lux 验收；Night 还要核对其目标亮度成对采样。三种模式都必须检查最终 `0x38` 使用的是稳定窗口数据，而不是过渡期单点。

### 11.2 本批次真机通过标准

- 所有参与灯具在每个采样点均被确认到位。
- OFF、搜索点和 ON 都由稳定窗口产生，不存在零样本通过。
- 目标可达性结论与稳定后的能力数据一致。
- `0x38`、`0x39` 和 publish delta 都收到正确成功 ACK。
- Sensor Publication、逐灯 Profile 和场景配置成功；任一失败均不恢复 Auto 并报告成功。
- 全部配置成功后才恢复 Group Auto。
- 同一环境重复校准所得关键 Lux/拐点落在约定容差内。

Auto 恢复后的最终 100 lx 收敛、响应速度和稳态误差属于下一阶段闭环验收；届时再增加稳定 Lux/逐灯 Lightness 的终态观测和长时间测试。

## 12. 建议决策

建议批准上述第一批范围，并采用以下默认选择：

- 统一稳定采样覆盖所有模式、所有亮度点；
- 最终值取稳定窗口代表值，不取全过程绝对极值；
- Group 使用 Unack 快速下发 + 逐灯单播核验/补偿；
- 零样本必须失败；
- Sensor 100% 稳定值及暗环境灯具贡献均以目标值的 95% 为最低可接受下限；
- 暗环境能力不足硬失败；
- Group 任一必要灯具离线或持续不到位时硬失败，不允许降级校准；
- publish delta 恢复必须成功，才能报告 SDK 成功；
- 暂不做断电持久化和 Auto 长期收敛验收。

具体采样抖动容差、稳定窗口和单点超时先作为可配置策略，通过当前三灯真机数据确定后再固化。目标达成容差固定为已确认的 5%，不得与采样抖动容差混用。
