# CPU 同步状态检查优化计划与边界

## 目标

依据 260915_1632_ipad_cpu_trace_analysis.md，先消除分组 Cell、设备页及进入空间后的同步状态检查重叠，再减少订阅/拓扑成员扫描，最后优化无变更清理的重复导出。

## 实施顺序

1. 三个入口共享按 owner 合并的刷新批次；计算使用现有 live Mesh 读取器，以主队列短片段执行，批次间让出 UI/蓝牙回调。此设计不将共享可变 Mesh 对象复制给更多后台线程。6 ms 是片段调度预算，单次函数调用不可抢占，实际最长片段必须测试。
2. 批次内共享节点分组索引、普通分组成员、空间拓扑和 Site Zone 目标。数据库 revision、账号、区域、当前网络及节点缓存失效代数变化时丢弃批次结果。
3. 订阅查询改用 SDK 已有单组 isSubscribed API；日程判断复用批次分组成员。SDK 本身不修改。
4. 无变更配置清理在两个数据库 revision 及时间戳仍一致时复用持久化导出；变更、恢复写入或 revision 不可用仍走完整回读，保留权限/恢复状态、拓扑和扩展数据校验。

## 验证

- 500 节点批次、重复 owner 请求、取消/复用、变化失效及无 revision 的保守处理。
- 优化和原始逐节点拓扑目标对比：普通组、退出失败、待加入成员、Space Zone 和 Site Zone 目标。
- 运行现有邻近照明、日程及恢复/清理测试，完成主 target 真机构建；新文件同步加入五个品牌 target。
- MtestiPhone15 已连接，优先用隔离测试工程运行生产计算/刷新代码；不操作 iPad LLH 的个人数据。最终需由人工在 iPad LLH 录制相同场景的 trace 比较 CPU。

本计划不等于完成报告，最终结果另行记录。
