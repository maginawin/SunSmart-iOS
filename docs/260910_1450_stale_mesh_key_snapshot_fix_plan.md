# 活动网络密钥快照过期修复计划

日期：2026-09-10。工作区：`site-trigger-zone`。状态：仅分析与规划，待确认实施。

## 结论

审查意见成立。建议保留 `SpaceMeshKeyStore.reconcile` 的全量密钥一致性保护，在共享调用协调入口增加一次有界刷新与重试，并将缓存过期与真实密钥故障分开处理。

本次自动恢复针对“数据库新增了其他 Space 的合法密钥，活动网络仍持有旧清单”的场景。采用重读数据库、验证差异、原位补齐活动对象密钥的方式，避免整体替换活动网络造成节点、分组及当前控制上下文脱节。密钥删除、已有值变化、绑定变化和 Key Refresh 变化不属于可自动补齐的差异。

## 当前证据

- `ExportData.swift` 的 `SpaceMeshKeyStore.reconcile` 先校验调用者和数据库快照，再比较全量 NetKey/AppKey 清单；不一致返回 `staleSnapshot`，不写入。这项保护有必要保留。
- `ImportData.swift` 的 `SpaceData.update` 优先复用同 Site、同 Network ID 的活动对象，其次复用 baseline，再从数据库加载。`preflight` 和 `reconcile` 失败均进入 `meshKeyFailure`，没有刷新分支。
- `SpaceConfigurationSafety.meshKeyFailure` 会保存 `meshKeys:<issue>` 阻断标记；`SpaceData.export` 入口遇到阻断直接返回。因此该问题先阻止导入，随后阻止上传；上传入口本身没有产生 `staleSnapshot`。
- Site 根级 `update` 同样复用活动主网络，将协调失败统一标记为 `meshKeyConflict` 并提前返回。
- `repairPreserved` 虽然使用独立新对象，加载与协调之间仍存在清单再次变化的窗口，且补齐后不会同步同 Site 的活动对象。
- Site 在等待子 Space 导入后，仍可能对先前持有的网络执行尾部 `save()`。刷新仅发生在根级导入开始时，不能保证尾部保存时清单仍新鲜。
- 已核对当前 `Package.resolved` 及相同提交 `a6246b1b0409824a3227a9c7cad8140219feb182` 的 SDK 缓存源码：`load` 读取全 Site 密钥；`save(allData: false)` 仍会覆盖整个网络记录，包括密钥清单；`add` 会更新本地 Provisioner 的密钥引用及时间戳，AppKey 还会绑定所属网络。Manager 的 `currentNetworkKey` 是单独缓存的对象，不能只替换 `meshNetwork` 就认为控制上下文已一致。

审查文档中的“连续三次失败、重载成功”为上一轮适配层复现记录，本轮未重新执行。当前测试只断言旧快照被拒绝，缺少调用方刷新后恢复的覆盖。

## 实施方案

### 1. 共享刷新协调入口

在 `SpaceMeshKeyStore` 周边提供调用方共用的协调入口，保留原 `reconcile` 作为单次检查和写入单元，避免在多个业务分支复制重试逻辑。

流程：

1. 按原逻辑尝试协调；成功直接返回，真实密钥错误沿用现有拒绝行为。
2. 仅遇到 `staleSnapshot` 时，按同一 mesh UUID 重新读取 Site 网络密钥清单。
3. 在修改活动对象前，完整验证两侧清单及全部差异：旧清单中的每把密钥必须在新清单中原值、索引、绑定、轮换状态一致；新增项必须完整、无索引冲突、无绑定歧义。不能只检查当前 Space 的一对密钥。
4. 所有差异验证通过后，将数据库已持久化的缺失 NetKey、AppKey 按顺序补入调用者对象。刷新本身不保存旧网络；已有密钥对象保持不变，保留节点、分组、场景、当前选择及未提交业务状态。显式检查 SDK `add` 对 Provisioner 和时间戳的影响。
5. 使用刷新后的同一对象重新执行原 `reconcile`，最多重试一次。密钥真正补齐仍由原路径保存并回读核对。
6. 若再次过期，返回可重试的暂时失败，本次不应用远端业务配置、不推进同步成功时间或回执、不写入持久密钥阻断。保留原有待处理状态，下次正常同步重新尝试。

删除、替换或轮换造成的差异不能用追加方式伪装为刷新成功，应返回明确的需复核结果并继续保护数据。实现中为此提供可区分的原因，避免永久返回一个没有恢复办法的普通缓存过期结果。

加载失败、保存失败沿用持久化失败处理，不将其吞掉或误报成功。刷新和重试复用现有锁；活动对象操作收敛到主执行上下文，并在接入处校验当前 Site/Space 身份。若必须跨 `await`，重新检查既有恢复上下文、版本和取消状态。

### 2. 接入完整调用链

- Space 正常导入：在现有密钥协调位置调用共享入口；后续拓扑校验、导入和导出继续使用完成刷新后的网络对象。保留拓扑异常时只补齐合法密钥的行为。
- Site 根级导入：接入相同入口，缓存过期不直接归类为持久密钥冲突；刷新成功后继续原导入流程。
- 保留本地变更的导入：`repairPreserved` 使用相同有界重试；仅修复密钥，不应用远端拓扑，不清除待上传、删除日志或恢复回执。对匹配的同 Site 活动对象执行同样的受控刷新，防止独立对象修复成功但活动上下文仍旧。
- Site 尾部保存：对本调用链中的最终网络保存增加最新清单核对与合法新增项刷新，避免子 Space 已补齐的密钥被旧清单覆盖。若无法安全协调，不执行该旧网络保存，也不将本轮标记为全部同步成功。这里仅保护该保存点，不扩展为全库事务或所有 SDK 写入路径重构。

### 3. 暂时失败与历史阻断恢复

- `meshKeyFailure` 增加防御分支，确保单纯 `staleSnapshot` 不再调用持久 `block`。真实缺失、冲突、绑定错误、轮换异常继续受保护。
- 已存在的 `meshKeys:staleSnapshot` 标记，通过正常导入/恢复入口的新鲜验证成功后解除，复用现有 `meshKeysRestored` 机制；不在启动时无条件批量删除。
- 自动重试仍过期时，保留已有持久状态，不调用 `meshKeysRestored`；历史标记也必须等验证成功才解除。
- 增加验收：已阻断的 Space 必须能再次进入导入重试，成功后可导出完整密钥并进入上传准备。仅尝试上传、未取得可验证的新鲜配置时，不绕过原导出保护。
- 复用适当的现有错误文案，不新增“刷新成功即云同步成功”的提示。若实施确需新文案，同步补充英文和简体中文。

## 回归测试与验收

| 场景 | 预期结果 |
| --- | --- |
| 活动 A 已加载，独立 B 补齐合法密钥，再导入 A | 本次自动刷新后成功；A、B 的完整密钥都保留；不写 stale 阻断 |
| 后续连续导入 A 三次 | 均不再因同一旧对象失败；幂等路径不新增密钥保存 |
| 活动 Site 主网络过期 | 根级导入可继续；子 Space 导入完成后的尾部保存不丢密钥 |
| 待上传本地恢复/删除期间收到远端配置 | 只补齐密钥并刷新活动上下文；业务配置、删除日志、回执保持 |
| baseline/独立网络在加载后再次过期 | 使用共享重试；超过一次则暂时失败，无死循环和新持久阻断 |
| 刷新期间切换 Site/Space、取消或恢复版本变化 | 不修改已失效的活动上下文，不推进导入成功 |
| 同索引不同密钥、绑定冲突、轮换或密钥删除 | 不覆盖、不重编号、不随机生成密钥，不误报刷新成功 |
| 新快照加载失败、补齐保存失败或回读不一致 | 返回对应失败，不生成成功回执 |
| 旧 `meshKeys:staleSnapshot` 标记 | 验证成功后解除，随后完整导出及上传准备可通过 |
| 其他保护状态同时存在 | 不清除删除日志、待导入文件、恢复回执或无关阻断 |
| 原位刷新前后 | 网络、已有密钥和业务对象身份稳定；当前 NetKey/AppKey 仍属于目标 Space |
