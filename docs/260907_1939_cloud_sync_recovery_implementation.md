## 1. 新增设备是否自动上传

**有自动上传策略。** Classic 和 Professional 添加完成后均发送 `spaceDataChangedNotificaitonName`，类型为 `network(.address)`。Space 页面调用 `commitLocalChangeForCloudSync`，推进 Space/Site 的本地版本，使用 `.syncSite(site:syncSpaces:)` 和 `.promptly` 入队；promptly 的等待时间为 0 秒。

因此，Synchronization failure 本身不能证明“没有启用自动上传”。该文案既用于实际云同步失败，也用于配置保护/恢复入口；需要点击后的正文和对应日志判断现场失败阶段。本轮已向用户询问提示是否持续及具体错误，尚未收到答复，未取得本次新增设备的请求日志。

源码中确认并修复的相关缺陷：

1. **首次上传未建立后续编辑基线。** `129444b` 确认上传时间和删除回执，但没有同时记录 `spaceConfigurationMigrated`。对于新建并完成首次上传的 Space，下一次添加设备可能被当作尚未完成升级基线校验，拿已新增设备的本地快照与新增前的云端快照比较，从而在真正提交新配置前被拒绝。
2. **重连没有主动恢复失败上传。** 原 Space 网络观察只恢复心跳；失败的同步 handle 会移出队列，不能保证无新编辑时重新上传/回读。
3. **旧失败信息与等待状态混杂。** `showSyncCloudError` 原来会优先返回旧错误，即使新任务已排队；导航栏对 wait 不做更新，也可能继续显示上一次失败。
4. **Site 导出可能使用旧 Space 对象。** 当前改动在调度及 Site 导出时对齐本次提交的 Space 实例，避免通知处理的版本与 Site 持有的对象不同。
5. **错误正文可能退化为“未知错误”。** 原回读错误用通用 apiError 包装，而现有 LocalizedError 对该类型返回 unknown_error。现在导出失败和回读未确认使用独立本地错误类型及持久化码，复用已有中英文提示，重新加载后也能区分；测试执行生产 NetworkApiError 的编码、解码及本地化入口。

以上是源码与自动化可验证的问题，不等于已确认其中一条就是本次真机现象的唯一原因。服务端拒绝、节点数据回读不一致、无网络等仍会正确显示失败。

## 2. 已实施的共享逻辑

### 上传与确认

- 新增本地 `SpaceRecoveryState`，沿用既有恢复存储作用域，保存完整身份、本地生命周期、实际提交时间戳、逻辑配置比较数据及提交阶段。没有添加认证字段或修改服务器协议。
- 普通云同步和 Space/Site 两处解绑入口复用提交准备、回读、回执持久化逻辑。
- 提交前保存待确认记录；请求被接受后记为 accepted；回读一致后先持久化 verified，再幂等完成删除回执、本地恢复回执及上传时间戳。
- journal 或数据库保存失败时保留 verified 任务，后续可仅重试本地确认，不显示整体完成。
- 确认仍使用实际提交版本，保留较新修改以及未完成的 prepared/removed 删除；同 UUID 重新配网和旧地址复用不再阻断 cleaned 回执结束。
- 首次上传确认时记录已建立基线。迁移旧版本状态时，在覆盖最近导出快照前，优先核对与已上传时间戳匹配的旧快照；升级核对的临时网络失败不再写成永久拓扑阻断。

### 自动恢复与首次 Site

- 重连、回到前台及进入 Space 时，对有权限且需要处理的配置任务重新调度。
- 待确认任务先执行只读回读，不依赖普通导出，更不依赖用户再次添加/编辑。
- 对有效但不同的响应，每轮最多回读 3 次；持续不同进入明确的冲突保护，保留审阅恢复入口。断网/超时保留任务等待后续事件，不无限轮询。
- 多 Space 的回读与回执分别保存，一个 Space 失败不撤销其他 Space 已完成的确认。
- 首次 Site 已接受的创建状态与资源仍保留；新增创建提交时间记录。在创建响应后、本地 Site 状态保存前中断，可通过 Site GET 核实创建及 provisioner，再继续 Space 确认，避免直接重复 siteAdd。
- 保留现有逻辑比较范围：Group Profile/Path、节点成员关系、Space Zone；provisioner 地址资源与设备观测缓存不参与该比较。

### 权限与重新授权

- 继续在逻辑配置保护前处理远端身份、角色、密码和成员元数据；读写接口的权限错误进入共享状态处理。
- 密码过期、账号授权失效进入等待授权，停止自动写入，保留待处理本地数据。普通网络错误不当作撤权。
- 明确 Visitor/撤权时保存旧恢复证据，退出旧写入意图并隔离旧生命周期。未完成设备清理不会被标成成功，也不会触发额外 Reset。
- Visitor 仍可读取时，要求应用通过既有校验的远端配置；不再被离线本地修改的较新时间戳挡住。
- 重新授权后先比较云端；存在本地待写且远端已变化时进入审阅，不能直接重放旧快照。
- 用户明确输入新密码且 GET 成功时，先更新验证状态，再进行导入，避免同一响应的旧密码事件立即重新挂起刚完成的验证。

### 解绑、本地删除与旧回调

- 两处解绑的上传部分均使用共享确认流程，读取失败或本地确认失败时不继续正常“保存后解绑”。
- 请求解绑前保存退出意图；结果未知可通过后续只读请求核实。已成功解绑的本地删除使用可恢复的 removing 状态。
- Space 的 Mesh/扩展/数据库删除改为完成后返回结果，调用方不再只依赖异步任务已经排队。
- Site 删除先记录各 Space 的删除生命周期；子项完成后再移除 Site 数据，保留中断重试入口。
- 归档先让旧恢复状态退出活跃集合；文件移动失败保存待归档路径，之后重试。重新导入使用新的恢复目录，不继承旧活跃回执。
- 提交、回读、设备删除上下文和审阅恢复操作校验捕获的身份/生命周期，防止旧回调确认或清理新导入的数据。
- 同时修正相关 Site 同步查询/取消中的变量遮蔽，确保删除一个 Site 不取消其他 Site 的任务。
