# WiFi Gateway OTA 取消 UI 需求合理性分析

## 结论

需求部分合理，但不能在“仅实现 `0x43/0x11`、不实现 `0x43/0x15`”的范围内完整交付。

- `Upgrade cancelled` 合理且可实现：`0x43/0x11` 的合法匹配 `CANCELLED` 是明确的取消成功终态，可展示该状态，并使用 `UPGRADE AGAIN`。
- `Failed to cancel` 的视觉设计合理，但当前没有协议真值来源：`0x43/0x11` 不包含“取消失败”阶段或错误码，不能仅凭状态查询判定取消失败。
- `CANCEL AGAIN` 当前不可执行：它必然需要再次发送取消命令，但 `0x43/0x15` 尚未提供且明确不在本轮范围内。

因此推荐本轮只实现 `Upgrade cancelled + UPGRADE AGAIN`；保留 `Failed to cancel + CANCEL AGAIN` 设计，等收到完整 `0x43/0x15` 协议后再规划实现。

## Figma 核对

### 取消成功

- Figma 节点：`332:6041`
- 状态文案：`Upgrade cancelled`
- 示例进度：`50%`
- 使用失败/提示色图标和文字。
- 底部按钮需求：`UPGRADE AGAIN`。

### 取消失败

- Figma 节点：`332:6053`
- 状态文案：`Failed to cancel`
- 示例进度：`50%`
- 使用失败/提示色图标和文字。
- 底部按钮需求：`CANCEL AGAIN`。

两个节点都沿用当前 WiFi OTA 进度组件结构：主题色进度条、右侧百分比、居中状态图标和文案。现有 `WiFiFirmwareUpdatingView` 可以通过新增状态分支复用，不需要新增页面或重建组件。

## 协议真值分析

| 场景 | `0x43/0x11` 是否能明确表达 | 本轮能否实现 |
| --- | --- | --- |
| 取消成功 | 是，合法匹配的 `CANCELLED` 终态 | 是 |
| 取消请求参数错误 | 否，属于未来取消命令 ACK | 否 |
| 取消请求超时 | 否，属于未来取消事务结果 | 否 |
| 取消后 OTA 继续推进 | `0x43/0x11` 只能表达 OTA 当前状态，不能单独证明取消命令失败 | 否 |
| 再次取消 | 否，必须发送未来 `0x43/0x15` | 否 |

`CANCELLED` 是首个合法终态时，本轮 OTA 结束。它不能被解释成取消失败。反过来，收到其它非终态、通信未知或查询超时，也不能直接解释为取消失败，因为 App 不知道取消请求是否已发送、是否被接受以及事务是否仍在进行。

## 现有 App 影响

- 当前 App 没有取消命令，下载和更新阶段的 `CANCEL` 按钮为禁用状态。
- 当前 UI 状态枚举没有 `cancelled` 或 `cancelFailed`。
- 当前主要按钮动作只有升级、重试升级、禁用取消和完成，没有再次取消动作。
- 当前 `alert_failed` 资源和进度组件样式可以复用；新增用户可见文案需要同步 English 和简体中文。

## 可选方案

### 方案 A：按协议能力拆分交付（推荐）

本轮新增 `cancelled` UI 状态。合法匹配的 `CANCELLED` 显示 `Upgrade cancelled`，保留最后有效进度，停止本轮状态查询，并提供 `UPGRADE AGAIN`。不新增 `cancelFailed` 和 `CANCEL AGAIN`。

优点：协议真值完整，范围与“仅实现 `0x43/0x11`”一致，不会创建无效按钮。

代价：两个 Figma 状态本轮只能交付一个。

### 方案 B：同时创建取消失败 UI，但保持不可达

预先新增 `cancelFailed` 展示状态和 `CANCEL AGAIN` 外观，但不把任何协议结果映射到该状态，按钮也无法执行。

优点：可以提前完成部分 UI 结构。

缺点：产生死代码和不可验收交互；未来 `0x43/0x15` 语义可能要求重做，不推荐。

### 方案 C：用查询失败或非 `CANCELLED` 状态推断取消失败

将查询超时、通信未知或取消期间继续收到其它阶段映射为 `Failed to cancel`。

缺点：这些现象都不能证明取消失败，会把通信问题或合法 OTA 进展错误归因；违反协议的首终态和通信未知规则，不应采用。

## 推荐验收边界

本轮只验收以下行为：

1. 合法匹配的 `CANCELLED` 被识别为失败之外的独立终态。
2. UI 显示 `Upgrade cancelled` 和最后合法进度。
3. 底部显示可用的 `UPGRADE AGAIN`，触发的是已有升级重试流程。
4. `CANCELLED` 后忽略同一轮后续状态。
5. 不新增、不发送、不模拟 `0x43/0x15`。
6. 不展示 `Failed to cancel`，不提供 `CANCEL AGAIN`。

未来收到完整 `0x43/0x15` 协议后，再根据取消 ACK、事务匹配、超时和重试约束补充 `Failed to cancel + CANCEL AGAIN`。
