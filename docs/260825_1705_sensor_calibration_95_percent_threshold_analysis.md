# Sensor Cal. 95% 与 0% Lux 阈值分析

> 2026-08-25 补充澄清：本文中的 95% 结论只针对 Sensor Cal. 的目标可达性判定。经产品语义再次确认，Sensor 的目标判定不得减 0% Lux；只有 Night Cal. 的目标值由成对的 `OnLux - OffLux` 产生。Plane Cal. 的倍率公式和三种模式共用的 `0x38` 曲线属于另外两层语义，详见 `260825_1708_calibration_on_off_lux_semantics_clarification.md`。

## 分析结论

本轮失败不是灯具未到位、Lux 未稳定、目标 295 lx 未达到，也不是 Vendor ACK 失败。真正失败点是当前 Sensor Cal. 对 95% 执行了两个连续硬门槛：

1. 100% 灯光下的总 Lux 必须达到 `targetLux × 95%`；
2. 再扣除 0% 灯光下的 Lux 基线，灯具独立贡献也必须达到 `targetLux × 95%`。

本 Log 第一项通过，第二项失败。第二项实际验证的是“假设环境底光完全消失后，灯具单独仍能达到目标的 95%”，这比“本次校准条件下灯已经尽力并达到目标允许范围”严格很多。按当前确认的产品方向，应保留第一项，取消第二项的硬失败语义；0% Lux 应作为校准曲线基线和灯光是否产生可测影响的依据，不应再与目标 Lux 的 95% 直接比较。

## Log 还原

### 目标下限

- Target：295 lx；
- 允许下浮：5%；
- 计算结果：`ceil(295 × 95%) = ceil(280.25) = 281 lx`。

### 0% 与 100% 稳定值

| 采样点 | 原始样本 | 稳定窗口 | 代表值 | 判定 |
| --- | --- | --- | ---: | --- |
| 初始环境 | 295、295、295、295 | 295、295、295、295 | 295 | 只证明开始时环境读数稳定，不是正式满亮能力点 |
| 0% | 81、56、48、46、46、46 | 48、46、46、46 | 46 | Group 三台必要灯具均已确认到 0，基线有效 |
| 100% | 267、286、292、294、295、295 | 292、294、295、295 | 295 | Group 三台必要灯具均已确认到 100%，正式满亮点有效 |

正式 100% 点的稳定代表值已经是 295 lx，并非只有一个瞬时样本碰到 295。当前稳定窗口算法对 `[292, 294, 295, 295]` 得到代表值 295，所以本轮不需要依赖初始环境样本，也不需要放宽为任意原始峰值才能通过总 Lux 门槛。

### 实际失败计算

- 满亮总 Lux：295 lx；
- 0% 基线：46 lx；
- 灯具贡献：`295 - 46 = 249 lx`；
- 总 Lux 达标率：`295 / 295 = 100%`；
- 灯具独立贡献达标率：`249 / 295 ≈ 84.4%`。

当前实现先判断 `295 >= 281`，结果通过；随后判断 `249 >= 281`，结果失败，因此输出：

- `success=false reason=dark_capacity`；
- `sensorDarkCapacityInsufficient(... measuredLux: 249)`。

回滚日志中的 `calibrationRestored=true`、`publicationRestored=true`、`publishDeltaRestored=true` 说明失败后的旧校准、Publication 和上报阈值均恢复成功，本轮没有留下部分提交状态。

最后一条 `failed` 中的 `sensorOnLux=0 sensorOffLux=0` 不是实测值变成了 0。当前成员变量只在目标可达性通过并写入 `0x38` 后才赋值；本轮提前失败，所以仍保留初始化值。排障时应以紧邻失败前的 `target_reachability` 中 295/46/249 为准。这属于日志可观测性问题。

## 对“最大值达到目标 95% 即可”的分析

产品方向合理，但建议把“最大值”限定为“灯具已确认到 100% 后，稳定采样阶段得到的有效值”，不要把整个校准过程中的任意原始峰值直接用于放行。

推荐判定为：

`100% 稳定代表 Lux >= ceil(targetLux × 95%)`

原因：

- 初始环境阶段没有绑定已确认的 100% Lightness，不能作为灯具满输出能力证据；
- 过渡期间的单个峰值可能来自传感器噪声、反光、人员遮挡变化或上一次灯光状态；
- 已稳定窗口可以避免错误放行，同时本 Log 的代表值本身就是 295，不会造成额外严格。

如果产品明确要求进一步宽松，可使用“100% 已验证到位后的稳定窗口最大值”与 95% 比较；仍不建议使用进入 100% 阶段后的全部原始样本最大值。对本 Log，这两种稳定口径都会通过。

## 0% Lux 阈值应如何调整

### 当前隐含阈值过严

当前暗环境能力门槛等价于：

`offLux <= onLux - ceil(targetLux × 95%)`

本轮 `onLux=295` 时，0% Lux 必须不高于 14 lx 才能通过；实测 46 lx，因此失败。更极端的是，如果满亮值刚好达到最低可接受值 281 lx，那么 0% Lux 必须等于 0 才能通过。

这会导致一个反直觉结果：环境底光越充足、实际满亮总 Lux 越容易达到目标，校准反而越容易因为扣除底光而失败。它已经偏离“当前条件下是否达到目标允许范围”的产品目标。

### Sensor 目标判定中的 0% 逻辑

Sensor 的目标可达性只判断 100% 稳定 Lux，0% Lux 不参与该判断：

`100% stableOnLux >= ceil(targetLux × 95%)`

因此 Sensor 目标判定不再计算 `stableOnLux - stableOffLux`，也不应新增任何基于该差值的硬门槛。0% 采样是否继续用于 `0x38` 曲线、Plane 倍率或灯光影响诊断，属于独立的协议/校准数学问题，不能再与 Sensor 目标 95% 混为一个成功条件。

### 建议取消或降级的 0% 逻辑

- 不要求 0% Lux 接近 0；正常日光、邻区光、窗外光和传感器底噪都可能形成非零基线；
- 不计算或判断 `onLux - offLux >= targetLux × 95%`；
- Sensor 的 0% Lux 不参与目标可达性成功/失败结论。

按这个规则，本轮结果应为：

- 满亮稳定代表值 295 >= 281：通过；
- 0% 基线 46 lx：不参与 Sensor 目标可达性判断；
- 后续协议曲线和 identity `0x39` 是否继续提交，由各自独立规则决定。

## 建议的边界用例

| Target / 0% / 100% | 建议结果 | 原因 |
| --- | --- | --- |
| 295 / 46 / 295 | 通过 | 满亮稳定总值达到目标，灯光贡献有效 |
| 295 / 0 / 280 | 失败 | 满亮稳定总值低于 281 lx |
| 100 / 30 / 120 | 通过 | 总值达到目标；90 lx 灯具贡献不足 95 lx 只记录风险，不硬失败 |
| 100 / 99 / 100 | Sensor 目标判定通过 | 目标判定不减 0%；曲线是否有效另行判断 |
| 100 / 100 / 100 | Sensor 目标判定通过 | 目标判定不减 0%；曲线是否有效另行判断 |
| 100 / 20 / 稳定代表 94，孤立峰值 100 | 失败 | 不应用单个噪声峰值掩盖稳定能力不足 |

## 实施范围建议

本轮仅完成分析，未修改业务代码。若确认实施，建议聚焦以下语义变更：

1. Sensor 可达性只用 100% 稳定代表值与目标 95% 下限做硬判断；
2. 从 Sensor 目标判定中完整移除暗环境贡献分支；
3. 更新对应错误枚举、本地化文案、数学测试和 App 源码契约；
4. 修正失败日志，使目标判定前也能输出实际 0%/100% 稳定值；
5. 真机覆盖高环境底光、低环境底光、临界 95% 和孤立峰值场景。

需要明确接受的产品边界是：校准时环境光帮助总 Lux 达标，但之后环境光下降时，灯具可能已经 100% 仍达不到目标。按“灯已经尽力，不因此拒绝校准”的原则，这应表现为运行时饱和和非阻断诊断，而不是校准失败。
