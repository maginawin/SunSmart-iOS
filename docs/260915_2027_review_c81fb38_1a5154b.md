## P2：无关空间的损坏拓扑污染当前空间状态

位置：`SunSmart/Common/Data/NodeSyncTopologyStorage.swift` 的 `Request.spaces` / `Request.read`。

当前空间 A 没有参与 Site Zone，而同一 Site 的空间 B 存在无法解码的 `triggerZones` 时，读取器仍会先加载并解码整个 Site 的全部空间。B 的异常使读取提前失败，无法进入后面的 `localOnly` 分支。调度器据此执行 `finishUnavailable()`，对 A 的全部请求返回需要同步，即使 A 中检查的是已同步、无 Vendor Model 的普通设备，也会错误显示同步标记或同步按钮。

回归边界：旧状态检查在无 Vendor Model、没有其他配置差异的场景下直接完成，不会调用邻近照明的 Space / Site 拓扑加载；新实现则在任何节点检查前强制完成全 Site 空间解码。

建议将当前空间与 Site 参与关系的读取，和其他空间的拓扑展开分开。无 Site 依赖时不应因其他空间拓扑损坏而失败；存在真实依赖时仍应保守拒绝不可用输入，不应把损坏拓扑当作空拓扑。

验证：临时 Swift 测试直接抽取生产 `Request.spaces`，配合真实 SQLite 库和生产 Space 列定义。A、B 数据正常时返回两个空间；仅把 B 的区域数据改为非法 JSON 后，整个生产读取函数抛错，而 A 的区域数据仍为合法空数组。临时测试没有访问账户数据库，且已随临时目录清理。最终 UI 影响通过调度器和调用方代码核对，未做真机复现。
