# 54804a0 代码审查：CPU 高占用的引入原因

## 审查范围与结论

- 审查提交：`54804a091cef27ddc5c782e27c225559587d8842`，对比父提交 `2e875e1f`。
- 当前 HEAD 是后续修复 `cf5e5c13`，本次结论针对被审查提交，而非认定修复后的 HEAD 仍有相同问题。
- 确认两处性能回归：恢复入口缺少候选筛选，以及 Zone 分类器无条件加载整站 Mesh。二者相互放大，造成主线程大量重复工作。

## 引入过程

### 1. 将完整清理接入所有空闲 Space 的前台恢复

`CloudSynchronizationManager.swift` 在被审查版本第 392–395 行新增循环，仅判断是否存在运行中的同步任务，不判断 Space 是否已同步、是否待上传或需要恢复。

既有的网络状态变化和 App 激活事件都会调用 `resumePendingSynchronizations()`。原来待上传筛选后的有限工作，现在在筛选之前就逐一进入完整清理。`SpaceSyncCleanupCoordinator.perform` 正常成功路径包含清理前导出和持久化读回导出；即使没有任何修改也不会跳过。

因此，“没有运行中的同步任务”被错误地当成了“需要执行恢复”。已同步 Space 也重复加载、导出和校验。

### 2. 每处理一个 Space，又扫描整站 Space

`SpaceSyncCleanupCoordinator.perform` 收尾调用 `cleanObsoleteMembers()`，后者先创建 `cleanupClassifier`。被审查版本 `SiteTriggerZoneTopologyReader.swift` 第 93–103 行在创建分类器时立即遍历全部可编辑且未阻塞的 Space，加载 Mesh、GroupInfo 并计算拓扑。

这个扫描发生在实际读取待清理成员之前，所以空 Zone、甚至没有成员需要分类时也会执行。每个 Space 清理完成都会重新创建分类器，缓存仅在单次创建内有效。

假设同一 Site 有 N 个符合清理条件的 Space，一轮恢复会执行约 N 次整站扫描，网络读取规模因而接近 N²。当前活动网络可以复用，但其他 Space 通常需要 `MeshNetwork.load`，包含解码和密钥处理。

### 3. 为什么 async 没有避免卡顿

恢复 Task 和清理协调器都运行在 MainActor。异步函数中的同步 Mesh 加载、拓扑计算和数据组装仍占用主线程；使用 Task/await 不等于把这些计算移到后台。

代码能确认的是有限的重复全量扫描，不是无限循环。重复 export 日志也不能单独证明死循环，或代表整个清理的耗时。
