## 3. 当前仍需补齐的具体边界

### 3.1 两个解绑入口没有统一

`SiteViewController.swift:2294–2325` 仍直接发送 spaceUpload，在 success 回调中将 `lastUploadCloudTimestamp` 设为**回调当时**的 `space.lastUpdate`，随后递归解绑；它没有调用共享回读或回执确认。

因此，从 Site 页面解绑时，“服务器接受请求但回读仍有旧 Node”以及“请求期间产生更新版本”这两个输入仍可能提前进入解绑。后续正常归档可以解决旧日志阻断重新导入，却不能证明离开前的配置已保存到服务器。

### 3.2 回读暂时失败被当作持久拓扑阻断

当前可从源码确认以下链路：

1. `verifyUploadedConfiguration` 对断网、身份错误和配置不一致均返回 Bool false（`SpaceConfigurationSafety.swift:147–164`）。
2. 普通云同步统一写入 `uploadReadbackUnconfirmed` 阻断标记（`CloudSynchronizationManager.swift:901–907`）。
3. 下次普通重试先导出；`ExportData.swift:335–336` 和 `prepareUpload` 拒绝被阻断的 Space。
4. 有删除/恢复回执时，普通 GET 导入又被 `preservesLocalChanges` 保留本地逻辑配置；现有确认方法也不清理该回读阻断原因。

这不是首次 Site 仍未执行回读，而是**已经执行回读后，失败没有独立恢复通道**。目前仍有用户主动恢复等路径，不能描述成任何操作都无法解除；但普通重试缺少自动收敛保障。

另一个同类边界：`confirmLocalChanges` 忽略 journal 写入的 Bool 结果，调用者仍可能推进上传时间戳、清除错误并报告成功。需要把“云端已验证”和“本地确认已持久化”区分开。

### 3.3 权限元数据更新不等于待上传操作已经退出

当前 `preservesLocalChanges` 仅看 journal 非空或本地恢复标记，不区分可写、等待重新授权、已撤销。Visitor 的 `needUploadCloud` 返回 false（`SpaceData.swift:126–127`），但回执仍使逻辑配置导入被保留；密码待验证则被 prepareUpload 拒绝。

上传错误分支仅记录 `syncCloudError`；回读错误通过 Bool 丢失业务错误分类。Space 页面心跳虽有密码和失权处理（`SpaceViewController.swift:1093–1145`），但后台同步和 GET 的处理不应依赖该页面心跳。

已存在可复用的错误枚举：noSitePermission、noSpacePermission、userUnauthorized、incorrectPassword、spacePasswordOverdue（`NetworkRequest.swift:353–405`）。账号授权失败不能直接当作永久 Space 撤权，断网也不能当作失权。

### 3.4 归档是一次尽力操作，删除完成边界不明确

`archiveDeletedSpace` 返回 Void；移动目录失败只打印日志，后面的活跃标记清理不执行。`Database.swift` 调用后仍可返回 true。

`SpaceData.delete()` 在 `MeshNetwork+SunSmart.swift:462–485` 异步删除扩展和 Space 数据，但立即返回 true。仅有成功归档测试，尚未证明数据库删除失败、归档失败、杀进程、快速重新导入和旧异步回调时仍可正确隔离生命周期。

上述判断来自当前源码分支和测试覆盖检查；本轮未进行真实文件故障注入或设备上的并发复现。

## 4. 推荐实现方案

### 4.1 统一提交、回读和确认，保留现有设备删除规则

在现有 Common 云同步/恢复模块内提取小范围共享操作，普通 Space 上传、Site 内嵌 Space 上传及两个解绑入口共同使用。控制器保留各自导航与提示，只将上传确认部分收口。

共享操作捕获不可变提交上下文：账号/区域、Site/Space/Mesh/子网身份、本地生命周期标识、实际提交时间戳和现有逻辑配置比较结果或其摘要。它返回明确结果：已验证且确认落盘、等待回读、权限待处理、配置冲突、持久化失败；不再仅用 Bool 区分所有情况。

- 继续使用当前 `cleaned && completedTimestamp <= submittedTimestamp` 规则；prepared/removed 不能被普通上传确认清除。
- 不要求 UUID 或旧地址永久不存在，不改变设备真实 UUID，也不为原第一项额外改 SDK/配网协议。
- 从请求捕获的提交版本推进确认时间，不使用完成回调时的最新 lastUpdate。
- journal 确认返回可检查结果；确认落盘失败时保留任务，重试本地确认，不能显示整个流程已完成或继续普通“保存后解绑”。
- 本地 journal、恢复标记和数据库时间戳跨存储更新采用幂等重放；不假设文件与数据库存在一个原子事务。进程中断后不能丢失待确认任务。
- Site 中多个 Space 按各自结果持久化；一个 Space 失败时，已经验证的其他 Space 不应丢失确认记录。

### 4.2 将待回读任务与拓扑阻断分开

上传前持久化提交上下文，成功响应后记录“已接受、待验证”；请求结果未知时记录“结果待核实”。本地只保存必要数据，并沿用恢复目录的文件保护与备份排除规则，不新增认证字段。

1. 首次 Site 保留 `129444b` 的“创建已接受”记录，后续不得因 Space 回读失败再次发送 siteAdd；同时检查创建状态的保存结果。
2. 回读超时/离线保留本地配置保护，进入待验证；重连、重新进入或显式重试时优先执行只读确认，不必再次调用被阻断的普通导出。
3. 单轮有限次数重试；本轮失败后保存任务，等待网络/前台/用户重试事件。不得形成无限轮询或依赖再次编辑。
4. 回读一致时，完成本地回执确认和对应任务清理；只能解除该提交对应的回读保护，不能删除 Profile 损坏、未完成导入等其他保护原因。
5. 回读有效但不一致时，不确认，不自动重写远端。保留已提交本地副本，有限回读后进入配置冲突/待处理状态，复用现有审阅恢复流程。
6. 错误身份与不可解析响应不得应用到当前 Space；请求前、await 返回后均校验捕获的生命周期，防止旧请求确认重新导入后的新状态。

沿用当前 `configurationData` 比较语义：它检查 Group Profile/Path、节点成员关系及 Space Zone，排除 provisioner 资源和设备观测缓存；不能把它称为所有业务字段的完整确认。此次不扩大为全部 JSON 字节相等校验，也不削弱现有成员检查。

### 4.3 为失权定义明确策略

权限、密码及成员事件仍先于拓扑应用。共享元数据处理结果通知同步调度器和现有页面权限流程；GET 成功中的 role/events 与直接返回的业务权限错误走同一决策入口。

| 情况 | 推荐处理 | 后续恢复条件 |
| --- | --- | --- |
| 仍有 Owner/Editor 权限 | 本地修改保护继续生效，正常提交或待回读 | 有效确认结束回执 |
| 密码变更、账号授权过期、会话暂时禁用编辑 | 持久化等待授权状态，停止配置写入重试，保留本地副本；权限刷新/密码验证不被拓扑保护拦截 | 重新授权后先读取云端并比较当前版本，不直接重放旧快照 |
| 明确降为 Visitor，仍可读取 Space | 保存未上传本地配置的诊断副本，将旧写入意图移出活跃上传集合；允许合法远端拓扑进入只读状态 | 后续恢复 Editor 权限不自动复活旧写入；有分歧时走已有审阅流程 |
| 服务端明确撤销 Space/Site 访问 | 停止该身份的配置操作，保留隔离诊断记录，按现有失权流程退出 | 重新分享/导入按新的本地生命周期处理 |
| 普通网络错误 | 待重试，不推断失权，不归档本地编辑 | 网络恢复后核实 |

失权处理必须区分“取消旧上传意图”与“完成设备清理”。prepared/removed 不得伪装成 cleaned，更不能因失权触发 Reset；本地尚未完成的删除清理需单独保留证据。归档只改变意图的活跃性，不代表服务器接受了删除。

推荐上述策略的原因：暂时认证失效时保住编辑；确定只读/撤权时，不再要求成功上传一个已无权上传的操作才能看到远端更新。

### 4.4 将解绑和恢复归档做成可重试的本地终止流程

保留按 Space 归档诊断资料的现有做法，新增最小的本地生命周期/终止记录，用来隔离解绑前后的异步工作。这里的生命周期标识属于本地 Space，不是设备 UUID、Mesh Key 或服务器版本。

推荐顺序：保存退出意图 → 如有权限且需保存，完成共享上传确认 → 请求解绑 → 记录远端解绑成功 → 等待本地 Mesh/数据库/扩展清理结果 → 使旧恢复集合退出活跃状态 → 搬移诊断目录并完成记录。

- 解绑失败不提前归档或清空有效回执；请求超时且结果未知时先核实服务端状态。
- 解绑已经成功但本地清理失败，保留终止任务供下次启动/进入重放，不能仅返回成功后丢掉后续工作。
- 文件搬移失败时，旧生命周期不能重新参与导入保护；归档搬移可延后重试。若连终止记录都无法持久化，则报告本地处理未完成，不静默解除保护。
- 快速重新导入要等待旧身份的删除阶段结束，或使用新生命周期明确隔离；旧回调无权创建新 journal、清除新回执或删除新导入数据。
- `deleteData`/`deleteAll` 需要传递真实删除、确认和终止处理结果；只改这些恢复调用所需的删除完成边界，不扩展为全项目数据库重构。
- 两个解绑 UI 入口均在共享流程完成后再导航；正常单 Space、Site 内多个 Space 删除都覆盖。

## 5. 已有数据迁移与兼容约束

1. 读取现有 journal 保持兼容；新增字段使用可选值/明确旧版默认值，不因缺字段把合法旧文件当损坏。
2. 对旧 cleaned 回执，仍要求匹配当前身份与已验证提交；缺 completedTimestamp 的异常记录保留待核实，不能按当前时间直接确认。
3. 对旧 `uploadReadbackUnconfirmed`，仅在找到当前身份的可核对提交副本时迁移为待验证；缺少证据则保留保护并进入审阅，不全量删除阻断标记。
